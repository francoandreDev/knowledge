Picture a shared shelf that started with exactly three official mugs. Every
time someone needed "a mug, but taller, just for this one event", they bought
one more and put it on the shelf. Nobody threw any away. Four years later the
shelf holds 37 mugs, the sign above it still says "3 mugs", and nobody
remembers why eleven of them are there.

That is Northwind Retail's button situation (an illustrative company, not a
real one). The system launched with three buttons, and the checkout
inconsistencies of year one disappeared within months. A new designer's
component audit now finds **37 button implementations**.

**Everyone agreed the system worked on day one. So how does a system that
worked get to 37 buttons, with no single moment anyone would call "where it
broke"?**

## Is this the same problem a design system was meant to solve?

**If the system exists and is the source of truth, why is it still
inconsistent?** Because this is a different problem from the one the system
was built for. A design system prevents _accidental_ inconsistency: teams
reinventing a button because nothing shared exists. **Design debt** is what
builds up _inside_ a system that already exists, through many small,
individually justified departures from it.

| Term               | What it is                                                                   | When it shows up                               |
| ------------------ | ---------------------------------------------------------------------------- | ---------------------------------------------- |
| Visual drift       | Teams reinventing the same thing differently because no shared system exists | Before a system, or on screens it has not hit  |
| Design debt        | Deliberate exceptions and leftovers accumulating inside an existing system   | Years into a system, under sustained deadlines |
| Orphaned component | A component in the library that almost nothing still uses                    | Late-stage debt, the byproduct of unpaid debt  |

The word "debt" is deliberate. Each exception is a loan: it buys speed today
and charges interest later, in confusion and copy-paste. The problem is not
that debt exists, it is that nobody is scheduled to repay it.

## How does debt actually pile up?

**Where does one "just this once" exception go after the deadline passes?**
Usually nowhere. It is forgotten, or worse, it gets copied: the next person
under pressure searches the codebase, finds it, and assumes it is sanctioned.

```mermaid
flowchart LR
    D["Deadline pressure"] --> E["One-off exception<br/>ships outside the system"]
    E --> F{"Reviewed: fixed<br/>or formally adopted?"}
    F -->|"Rarely, in practice"| G["Exception becomes<br/>invisible precedent"]
    G --> H["Next deadline:<br/>copied or re-invented"]
    H --> D
    F -->|"Yes"| I["Debt repaid,<br/>system stays coherent"]
```

Four distinct mechanisms feed that loop:

| Mechanism             | What happens                                                                    |
| --------------------- | ------------------------------------------------------------------------------- |
| Unreconciled one-offs | A component built "just for this campaign" outlives it; nobody owns removal     |
| Orphaned components   | Pieces that shipped features have replaced stay in the library as false options |
| Governance decay      | The review step (a team, a lint rule, a sign-off) quietly stops being enforced  |
| Silent forking        | A squad copies a component locally to go faster; "later" never reconciles it    |

## What changes once the system is big?

For a small system, "governance" means the person who built it remembers
every decision. That stops working at scale. At scale governance is a
**standing process**: someone owns reviewing new exceptions, a written
threshold says when an exception becomes a first-class variant, and a regular
audit retires orphans before they become precedent.

Design debt does not mean the system failed. Any system under multi-year
deadline pressure accumulates some. What separates a coherent system from a
patchwork is whether something is paying the debt down on purpose, on a
schedule.
