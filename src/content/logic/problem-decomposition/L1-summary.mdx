"Make checkout faster" isn't actually a task anyone can start on Monday
morning — there's no single line of code that "makes checkout faster."
**What has to happen before this vague request turns into something a
specific engineer can actually pick up and solve?**

Measuring where the 4.2 seconds actually goes turns one unsolvable-as-
stated problem into four small, specific, independently attackable ones:
300ms of network time, 800ms of server processing, 2,500ms of database
query time, 600ms of client rendering. **Only one of those four numbers
is worth anyone's attention this week.**

</Scenario>

- **A vague problem often isn't actually intractable — it's just too
  coarse-grained to act on.** "Make checkout faster" and "reduce the
  database query from 2,500ms to under 500ms" describe the same
  underlying goal, but only the second one is something a specific
  person can start working on today.
- **Decomposition means breaking a problem into pieces that are each
  smaller, well-defined, and independently attackable** — not just
  splitting a sentence into shorter sentences, but identifying genuinely
  separate sub-problems that don't require solving each other first.
- **A useful decomposition should cover the whole original problem and
  its pieces shouldn't overlap.** If the pieces don't add up to the
  original problem, something's missing; if two pieces double-count the
  same underlying cause, "fixing" one will make the other look better
  without anything actually having changed.
- **Decomposition often reveals where effort should actually
  concentrate.** Before measuring, "make checkout faster" implicitly
  suggested working on everything at once. After measuring, it's obvious
  that fixing network time (300ms out of 4,200ms) would barely register,
  while the database query (2,500ms, nearly 60% of the total) is the
  entire problem in miniature.
- The practical skill this unit builds: **treating "I don't know where to
  start" as a signal to decompose, not a signal that the problem is too
  hard** — and checking that a proposed decomposition actually covers the
  whole problem without double-counting any part of it.

## From one vague ask to four measurable pieces

|                                | Before decomposition             | After decomposition                                      |
| ------------------------------ | -------------------------------- | -------------------------------------------------------- |
| What you know                  | Checkout takes 4.2 seconds total | Network 300ms, server 800ms, DB 2,500ms, rendering 600ms |
| What you can start working on  | Nothing specific                 | The database query — the dominant, independent piece     |
| How you'd know if a fix worked | "Does it feel faster?"           | "Did the DB query's 2,500ms actually drop?"              |
