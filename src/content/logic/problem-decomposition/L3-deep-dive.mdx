## Decomposing the total into measurable, independent stages

Before the JavaScript, the whole idea is arithmetic:

| Check                 | No-code version                                       |
| --------------------- | ----------------------------------------------------- |
| Total                 | Add all stage times                                   |
| Share of total        | Divide a stage's time by the total                    |
| Priority              | Start with the largest useful stage                   |
| Exhaustive            | The stage sum equals the independently measured total |
| Possible double count | The stage sum is greater than the true total          |

The functions below do those checks repeatably. They are not the point
of decomposition; they are a way to keep the decomposition honest once
you have named the pieces.

```js
function decomposeTiming(stages) {
  const total = stages.reduce((sum, s) => sum + s.ms, 0);
  return stages.map((s) => ({
    name: s.name,
    ms: s.ms,
    shareOfTotal: s.ms / total,
  }));
}
```

```js
const measurements = [
  { name: "network", ms: 300 },
  { name: "server-processing", ms: 800 },
  { name: "db-query", ms: 2500 },
  { name: "client-rendering", ms: 600 },
];

decomposeTiming(measurements);
// [
//   { name: "network", ms: 300, shareOfTotal: 0.071 },
//   { name: "server-processing", ms: 800, shareOfTotal: 0.190 },
//   { name: "db-query", ms: 2500, shareOfTotal: 0.595 },
//   { name: "client-rendering", ms: 600, shareOfTotal: 0.143 },
// ]
```

| Function                    | Plain job                                 |
| --------------------------- | ----------------------------------------- |
| `decomposeTiming`           | Calculate how much each piece contributes |
| `identifyBottleneck`        | Find the largest piece                    |
| `isExhaustiveDecomposition` | Check whether something is missing        |
| `hasOverlap`                | Check whether something was counted twice |

## Identifying which piece is worth attention

```js
function identifyBottleneck(decomposedStages) {
  return decomposedStages.reduce((max, s) => (s.ms > max.ms ? s : max));
}

identifyBottleneck(decomposeTiming(measurements));
// { name: "db-query", ms: 2500, shareOfTotal: 0.595 }
```

This is the concrete output of decomposition: not just four numbers, but
an unambiguous answer to "where should someone actually start" —
`db-query`, at 59% of the total, dwarfing everything else.

## Checking that a decomposition is exhaustive

```js
function isExhaustiveDecomposition(stages, measuredTotal) {
  const sum = stages.reduce((s, x) => s + x.ms, 0);
  return sum === measuredTotal;
}

isExhaustiveDecomposition(measurements, 4200); // true — the pieces account for the whole thing
isExhaustiveDecomposition(measurements, 5000); // false — 800ms is unaccounted for somewhere
```

A `false` result here is a genuine signal: if the pieces don't sum to the
independently-measured total, some real contributor to the 4.2 seconds
isn't represented in the decomposition at all — a hidden cache miss, a
retry loop, something not yet named as one of the four stages.

<Checkpoint question="isExhaustiveDecomposition(measurements, 5000) returns false. Does that tell you WHICH stage is wrong, or just that something is wrong somewhere?">

Just that something is wrong somewhere — the function only compares a sum
against an independently-measured total, it has no way to attribute the
800ms gap to any particular stage. Knowing the check failed is the start
of an investigation, not the end of one: the next step is finding what's
missing (a retry, a cache miss, a stage nobody thought to measure), the
same way a mismatched receipt total tells you a purchase is missing from
the list without telling you which one. The function's job is narrowly
to catch that the decomposition is incomplete, not to diagnose why.

</Checkpoint>

## Detecting a false, overlapping decomposition

```js
function hasOverlap(stages, trueTotal) {
  const sum = stages.reduce((s, x) => s + x.ms, 0);
  return sum > trueTotal;
}
```

```js
// A believable-looking BUT overlapping decomposition: "server-processing"
// was measured in a way that already includes the DB query's time inside it
const overlappingStages = [
  { name: "server-processing-incl-db", ms: 3300 }, // double-counts db-query
  { name: "db-query", ms: 2500 },
  { name: "network", ms: 300 },
  { name: "client-rendering", ms: 600 },
];

hasOverlap(measurements, 4200); // false — the real decomposition, no overlap
hasOverlap(overlappingStages, 4200); // true — sum (6700) exceeds the true total (4200)
```

The overlapping version isn't obviously wrong just by looking at it — all
four numbers look like real measurements. It's only checkable by
comparing the sum against the independently-measured true total, which is
exactly why the exhaustive/non-overlapping checks matter as actual code,
not just a one-time mental sanity check.

<Checkpoint question="Someone argues 'overlappingStages can't be a real problem — every individual number in it is a real, honestly-measured time.' What's wrong with that defense?">

Each individual number can be honest and the decomposition can still be
false, because the property that matters isn't whether any one
measurement is accurate — it's whether the pieces, as a set, double-count
a cause. "server-processing-incl-db" at 3,300ms is a perfectly real
measurement of how long server processing plus the database query
together took; the problem is only visible when it's placed alongside
"db-query" as if the two were separate, independent contributors. That's
exactly why `hasOverlap` checks the sum against the true total instead of
checking any single stage in isolation — overlap is a property of how the
pieces relate to each other, not a property any one piece can fail on its
own.

</Checkpoint>

## Extend the example: a decomposition that isn't purely additive

**The checkout example is additive — the four stages happen one after
another, so their times simply sum. What if a vaguer problem's pieces
don't sum, but instead depend on each other in more complex ways?**

Consider "our onboarding is confusing" instead of "checkout is slow."
There's no single total number, and a naive decomposition into
"confusing for new users" and "confusing for returning users" might look
independent but actually share a root cause (an ambiguous button label
that confuses everyone, just noticed differently by each group). The
additive structure of the checkout example is a special case that made
exhaustive/non-overlapping checks easy to compute directly — most
real-world decompositions require more judgment to verify the same two
properties, but the properties themselves (does this cover the whole
problem, do any two pieces share a cause) still apply.

For a non-additive problem, the output may be a hypothesis matrix rather
than a sum:

| Step          | User affected       | Evidence              | Possible cause          | Check next            |
| ------------- | ------------------- | --------------------- | ----------------------- | --------------------- |
| Invite email  | New team members    | Low open rate         | Subject looks generic   | A/B test subject line |
| Profile setup | Non-technical users | Many abandoned forms  | Required fields unclear | Watch a setup session |
| First project | Managers            | Repeated help tickets | Button label ambiguous  | Rename in prototype   |

The same discipline applies: cover the whole journey, avoid naming the
same cause twice, and choose the hypothesis with the strongest evidence.
If you want to go deeper on the technical pieces, `systems/query-planning`
and `systems/indexing` explain database query behavior, while
`web/render-performance` expands the rendering side.

## Failure modes

| Failure mode                                                                             | What it gets wrong                                                                                           |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Treating "I don't know where to start" as a signal the problem is unsolvable             | It's usually a signal the problem hasn't been decomposed yet, not that it can't be                           |
| Splitting a problem into pieces without checking they sum to the whole                   | A real contributing cause can hide entirely outside the named pieces                                         |
| Measuring two pieces in a way that double-counts the same underlying cause               | Fixing one piece inflates the other's apparent improvement without anything real changing                    |
| Assuming a proposed split's pieces can each be worked on independently, without checking | A piece that secretly depends on another isn't really separate — it's the same problem with two labels       |
| Spreading effort evenly across all decomposed pieces instead of the dominant one         | Decomposition's real value is revealing where the effort should concentrate, not just producing more numbers |
