It's Wednesday's planning meeting. The product manager needs a rough
number by Friday to decide whether to raise a storage budget request this
quarter — not a precise number, a _directionally correct_ one. **Nobody
has built the feature yet. Nobody has anything to measure. What do you
say when someone needs an answer to a question you have no data for?**

One engineer volunteers to build a staging replica and load-test it —
a real, accurate measurement, ready in two weeks. Another picks up a
marker: "active users times events per user per day times bytes per
event times days in a year." Four numbers, each a rough guess, multiplied
together in five minutes. Six months after launch, the real measured
number comes in at about 1.9 TB for the year. **The five-minute guess
said 1.5 TB — off by about 25%, not by 10x, not by a random amount in
either direction.** The two-week measurement would have been more
precise, but the budget decision was due Friday, and a number within
30% was already good enough to act on.

## What just happened on that whiteboard

No one measured anything. No one guessed the final number directly
either — a direct guess at "how many terabytes" would have been a coin
flip between wildly wrong and accidentally right. Instead, the unknown
was broken into smaller unknowns that were each easier to reason about:

| Factor                     | Rough estimate | How it was reasoned, not measured                   |
| -------------------------- | -------------- | --------------------------------------------------- |
| Active users               | ~200,000       | "We're around 180–220k on the last dashboard I saw" |
| Events logged per user/day | ~40            | "A few clicks, a few page views, maybe 30–60"       |
| Bytes per event            | ~500 bytes     | "A JSON blob with a few fields — 300–800 bytes"     |
| Days per year              | 365            | Known exactly, no estimation needed                 |

Multiplying those four numbers together — 200,000 × 40 × 500 bytes ×
365 — gives roughly 1.5 terabytes for the year. **This technique is
called Fermi estimation** (after physicist Enrico Fermi, known for
quickly estimating things like the number of piano tuners in a city with
no directory to check): produce a usable order-of-magnitude answer to a
question that can't be looked up or measured directly, by decomposing it
into a chain of smaller quantities that each _can_ be reasoned about with
real confidence.

## Key terms

- **Fermi estimate** — a fast, structured guess at a quantity, built by
  multiplying several individually-estimated factors together, rather
  than guessing the final number directly.
- **Order of magnitude** — a power-of-ten range (is it closer to 10,
  100, or 1,000?). Fermi estimation asks you to be right about the order
  of magnitude of each factor, not the exact value.
- **Decomposition factor** — one of the smaller, individually-estimable
  quantities a Fermi estimate multiplies together (users, events per
  user, bytes per event, days per year, in the example above). This is
  the same decomposition instinct `logic/problem-decomposition` teaches
  generally, applied specifically to numeric estimation.
- **Back-of-envelope reasoning** — another common name for this style of
  estimate, from the idea that it's quick enough to sketch on whatever
  scrap of paper is nearby.
- **Sanity check / reference point** — comparing an estimate's output
  against something already known, to catch an estimate that's off by
  an order of magnitude before anyone acts on it.
- **Error cancellation** — the reason a multi-factor Fermi estimate tends
  to land closer to the truth than a single wild guess: each factor's
  error is about as likely to run high as low, so the errors partly
  offset each other in the product instead of all stacking in the same
  direction. L2 makes this concrete with numbers.

The five-minute estimate wasn't precise. It didn't need to be — it needed
to be close enough, fast enough, to make a Friday budget decision instead
of blocking two weeks on a measurement nobody had time to wait for.
