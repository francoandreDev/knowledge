## Modeling the decision

Each option is a name plus a score (1-10, worst to best) on every
criterion. Each weighting is a plain object whose values sum to 1.0:

```js
const options = [
  {
    name: "stay-monolith-modular",
    scores: {
      operationalRisk: 8,
      teamFamiliarity: 9,
      maintainability: 4,
      timeToValue: 9,
      cost: 8,
    },
  },
  {
    name: "extract-2-services-now",
    scores: {
      operationalRisk: 5,
      teamFamiliarity: 5,
      maintainability: 9,
      timeToValue: 4,
      cost: 4,
    },
  },
  {
    name: "full-microservices-migration",
    scores: {
      operationalRisk: 2,
      teamFamiliarity: 2,
      maintainability: 8,
      timeToValue: 2,
      cost: 2,
    },
  },
];

const baselineWeights = {
  operationalRisk: 0.3,
  teamFamiliarity: 0.25,
  maintainability: 0.2,
  timeToValue: 0.15,
  cost: 0.1,
};
```

Nothing here is a measurement — every score and every weight is
someone's honest 1-10 judgment call, written down instead of left in
someone's head. That's the whole point: not to manufacture false
precision, but to make each individual judgment call visible and
arguable on its own.

## Weighted scoring

```js
function weightedScore(option, weights) {
  return Object.keys(weights).reduce(
    (total, criterion) => total + option.scores[criterion] * weights[criterion],
    0,
  );
}

function rankOptions(options, weights) {
  return options
    .map((option) => ({
      name: option.name,
      score: weightedScore(option, weights),
    }))
    .sort((a, b) => b.score - a.score);
}

rankOptions(options, baselineWeights);
// => [
//   { name: "stay-monolith-modular", score: 7.6 },
//   { name: "extract-2-services-now", score: 5.55 },
//   { name: "full-microservices-migration", score: 3.2 },
// ]
```

Under the baseline weighting, "stay monolith" wins by a real margin —
2.05 points out of 7.6, not a coin flip. **If the team stopped here,
what would they actually be trusting: the underlying decision, or one
person's first guess at how much operational risk should count?**

<Checkpoint question="weightedScore multiplies each criterion's score by its weight and sums the results. If a weighting object accidentally summed to 1.3 instead of 1.0, would rankOptions still correctly identify which option scores highest relative to the others?">

Yes, for picking a winner specifically — every option's score gets
inflated by roughly the same proportion, so the relative order
between options is usually preserved. But the absolute scores stop
meaning anything comparable across different weightings (a 7.6 under
weights summing to 1.3 isn't the same kind of 7.6 as one under weights
summing to 1.0), which breaks exactly the sensitivity analysis below —
comparing a top2Gap of 2.05 under one weighting against 0.5 under
another only means something if every weighting was normalized to the
same total first.

</Checkpoint>

## Sensitivity analysis: don't trust the first guess

**Priya, Marcus, and Dana from L1 would each honestly write down a
different weighting if asked. Whose weighting is "correct"? And if
that question doesn't have a clean answer, what does?**

Nobody's weighting is uniquely correct — which is exactly why the
recommendation shouldn't rest on only one of them. `sensitivityAnalysis`
reruns the same scoring under several plausible weightings and reports
whether the winner holds, and by how much:

```js
function sensitivityAnalysis(options, weightSets) {
  return weightSets.map(({ label, weights }) => {
    const ranked = rankOptions(options, weights);
    return {
      label,
      winner: ranked[0].name,
      top2Gap: ranked[0].score - ranked[1].score,
    };
  });
}

const weightSets = [
  { label: "baseline", weights: baselineWeights },
  {
    label: "risk-averse (Marcus)",
    weights: {
      operationalRisk: 0.4,
      teamFamiliarity: 0.2,
      maintainability: 0.2,
      timeToValue: 0.1,
      cost: 0.1,
    },
  },
  {
    label: "onboarding-first (Dana)",
    weights: {
      operationalRisk: 0.2,
      teamFamiliarity: 0.4,
      maintainability: 0.15,
      timeToValue: 0.15,
      cost: 0.1,
    },
  },
  {
    label: "3-year-outlook",
    weights: {
      operationalRisk: 0.15,
      teamFamiliarity: 0.1,
      maintainability: 0.5,
      timeToValue: 0.15,
      cost: 0.1,
    },
  },
];

sensitivityAnalysis(options, weightSets);
// => [
//   { label: "baseline",               winner: "stay-monolith-modular",  top2Gap: 2.05 },
//   { label: "risk-averse (Marcus)",   winner: "stay-monolith-modular",  top2Gap: 1.90 },
//   { label: "onboarding-first (Dana)",winner: "stay-monolith-modular",  top2Gap: 2.60 },
//   { label: "3-year-outlook",         winner: "extract-2-services-now", top2Gap: 0.50 },
// ]
```

Three of the four weightings — including both Marcus's and Dana's own
stated priorities pushed to their weighting's extreme — still favor
"stay monolith," comfortably. That's a genuinely robust result: the
recommendation doesn't depend on whose exact weight guess you use, as
long as it's in a plausible range. **But the fourth weighting — someone
arguing "we should be optimizing for the system we'll have in three
years, not for this team's current comfort" — is also plausible, and
under it, the winner flips**, and the margin (0.50 out of 6.75, about
7%) is thin.

<Checkpoint question="Three weightings say 'stay monolith,' one says 'extract now.' Is the honest conclusion 'three votes beat one, go with the majority weighting'?">

No — sensitivity analysis isn't a vote, and counting weightings that
way smuggles back in exactly the false precision this whole exercise
was meant to avoid. What it actually shows is that the decision is
robust to _most_ plausible disagreement about weights, but not to
_all_ of it — specifically, it hinges on how much the team should
discount current comfort in favor of a longer time horizon. That's a
real, substantive question about the business, not a tiebreak that
majority-counting weightings can resolve. Naming it precisely is the
useful output here, not picking a winner by counting.

</Checkpoint>

## Resolving a flip without more math

Once the flip is found, the temptation is to compute harder — argue
about the fourth decimal place of the maintainability weight until
someone wins. That's the wrong move: the weights were never that
precise to begin with, and squeezing more precision out of an honest
guess doesn't make it less of a guess. What actually resolves a case
like this is a different kind of question entirely:

- **Reversibility.** Extracting 2 services now can be partially undone
  — folded back if it goes badly, at some real but bounded cost.
  Committing to full microservices later, after more surface area has
  grown around the current boundaries, gets more expensive to reverse
  the longer it's deferred. If "stay monolith" is chosen and turns out
  wrong, is that mistake still cheap to fix a year from now, or does
  the cost of reversing it grow the longer the team waits?
- **Who bears the cost of being wrong.** If risk was underweighted and
  an incident happens, the on-call rotation absorbs that badly, at
  3am, not in a retro slide. If maintainability was underweighted, the
  team six months from now inherits a harder codebase to change safely.
  Those costs land on different people — which one is this team
  actually more willing to risk imposing on someone?
- **What you'd regret more.** Not a vague gut check, but a specific
  one: a year from now, would the team be more upset having split too
  early and paid an operational-maturity tax they weren't ready for,
  or having stayed monolithic too long and paid a much larger
  migration bill once the codebase had grown further around the old
  boundaries?

None of those three questions has a formula. They're exactly the kind
of judgment a weighted matrix was never going to replace — it narrowed
a shapeless three-week argument down to one specific, well-understood
disagreement (how much to discount current comfort for a longer time
horizon), and that's the most a structured framework like this should
be expected to do. The decision still gets made by a person, on
purpose, with the trade-off fully visible instead of buried.

<Checkpoint question="After the sensitivity check, the team decides to extract 2 services now, explicitly citing reversibility and the 3-year-outlook weighting rather than the top-line score. Was building the weighted matrix wasted effort, since the score didn't end up deciding it?">

No — the matrix did the load-bearing work even though its number
wasn't the final word. Without it, the team would still be arguing in
circles the way L1 opened: three unstated priorities, no shared
vocabulary for what the disagreement even was. The matrix converted
that into "the decision hinges specifically on how much to weight
long-term maintainability versus current team comfort" — a precise,
nameable crux — and the sensitivity check is what surfaced that crux
existed at all, instead of the team confidently shipping the baseline
weighting's answer without ever knowing how fragile it was. The score
not being the final word is the framework working as intended, not
a sign it failed.

</Checkpoint>

## Extending past this one worked example

This unit's worked example holds two things fixed that real decisions
rarely hold still: the list of criteria, and everyone's raw 1-10
scores. Two questions worth sitting with, not answered here:

**What should change in `sensitivityAnalysis` if a new criterion
surfaces mid-decision** — say, a compliance requirement nobody had
weighed at all shows up three weeks into the discussion? Rerunning the
existing weight sets with the new criterion simply missing from them
understates every option unevenly (whichever option happens to score
well on the _unweighted_ new criterion is quietly being shortchanged).
The honest fix isn't patching the old weight sets — it's treating the
new criterion's arrival as a reason to restart from L2's step 1,
because every existing weight was implicitly calibrated against a
different, incomplete list.

**What should change if two people don't disagree about a weight at
all, but about a raw score** — say, Marcus rates "extract 2 services
now" a 5 on operational risk, and a site-reliability engineer who
actually ran the last migration insists it's a 2? That's a different
kind of disagreement than a weight dispute, and sensitivity analysis
as built above doesn't cover it — it only varies weights, holding
scores fixed. Resolving a scoring disagreement usually means finding
out who has the better evidence for that specific number (incident
history beats a hunch), not re-running more weightings; conflating the
two kinds of disagreement is a common way this framework gets misused
in practice.
