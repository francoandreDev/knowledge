Two engineers agree on the rule out loud: "a user can edit a document
if they're not an admin, and they're either logged in or the owner."
One of them writes `!isAdmin && isLoggedIn || isOwner`. It reads like
a direct translation of the sentence — `not admin`, `and`, `logged in
or owner`. Weeks later, a security review finds that an admin who
happens to also own a document can edit it, which the spec explicitly
said should never happen. **The code looks like it says exactly what
was agreed. What actually went wrong?**

## Before reading the code

Boolean logic is about rules that can answer only **true** or
**false**: yes/no, allowed/blocked, included/excluded. The variable
names are written like questions:

| Code             | Read it as                                 |
| ---------------- | ------------------------------------------ | --- | ---------------------------------- |
| `isAdmin`        | "Is this user an admin?"                   |
| `isLoggedIn`     | "Is this user logged in?"                  |
| `isOwner`        | "Is this user the owner?"                  |
| `true`           | Yes, this part of the rule is satisfied    |
| `false`          | No, this part of the rule is not satisfied |
| `!isAdmin`       | Not an admin                               |
| `&&`             | AND: both sides must be true               |
| `                |                                            | `   | OR: at least one side must be true |
| Parentheses `()` | Group this part first, like arithmetic     |

So the intended sentence is:

`not admin AND (logged in OR owner)`

The buggy code is grouped as:

`(not admin AND logged in) OR owner`

That small change moves `owner` outside the "not admin" veto.

## The shape of the problem

- Boolean operators have a fixed precedence — `&&` binds tighter than
  `||`, the same way `*` binds tighter than `+` in arithmetic — so an
  expression with both, written without parentheses, doesn't parse the
  way a spoken English sentence with "and"/"or" naturally groups.
- Negating a compound condition isn't just "flip every `&&` to `||`
  and negate each piece" applied carelessly — De Morgan's laws say
  _which_ operator swaps with which, and getting that backwards
  produces a negation that looks plausible but is wrong for some
  inputs.

## Key terms

- **Operator precedence** — the fixed order in which `!`, `&&`, and
  `||` are evaluated when an expression has no parentheses; `!` first,
  then `&&`, then `||`.
- **Truth table** — a table listing every possible combination of
  inputs to a boolean expression alongside the result for each one —
  the only way to be certain two expressions are equivalent for _all_
  inputs, not just the cases that happened to be tested.
- **De Morgan's laws** — the two rules for negating a compound boolean
  expression correctly: `!(A && B)` equals `!A || !B`, and `!(A || B)`
  equals `!A && !B` — the operator flips when the negation moves
  inside.
- **Short-circuit evaluation** — `&&` and `||` stop evaluating as soon
  as the result is determined (a false `&&` operand, or a true `||`
  operand), which matters for readability but doesn't change _what_
  the final boolean result is.

## What this unit covers

L2 works through exactly why `!isAdmin && isLoggedIn || isOwner`
doesn't mean what it sounds like, using precedence rules and a truth
table to show precisely where it diverges from the intended rule. L3
implements the buggy and fixed versions as real functions, brute-forces
every input combination to prove they differ, and then builds the
correct negation using De Morgan's laws — showing what happens when
that negation is done carelessly instead.
