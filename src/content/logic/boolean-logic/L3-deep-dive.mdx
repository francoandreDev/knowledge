## The two versions as real functions

First, the same proof on paper:

| isAdmin | isLoggedIn | isOwner | Buggy result | Fixed result | Disagree? |
| ------- | ---------- | ------- | ------------ | ------------ | --------- |
| true    | true       | true    | true         | false        | Yes       |
| true    | true       | false   | false        | false        | No        |
| true    | false      | true    | true         | false        | Yes       |
| true    | false      | false   | false        | false        | No        |
| false   | true       | true    | true         | true         | No        |
| false   | true       | false   | true         | true         | No        |
| false   | false      | true    | true         | true         | No        |
| false   | false      | false   | false        | false        | No        |

The code below automates that same table. If you are new to code:
`function` names a reusable rule, `return` means "answer with this
value," `for` repeats work for several values, `console.log` prints what
was found, and `!==` means "is not equal to."

```js
// access.mjs
function canEditBuggy(isAdmin, isLoggedIn, isOwner) {
  return (!isAdmin && isLoggedIn) || isOwner;
}

function canEditFixed(isAdmin, isLoggedIn, isOwner) {
  return !isAdmin && (isLoggedIn || isOwner);
}
```

`canEditBuggy` is exactly what `!isAdmin && isLoggedIn || isOwner`
parses to without explicit parentheses — `&&` binds tighter than `||`,
so `isOwner` sits outside the `!isAdmin` check entirely.
`canEditFixed` makes the intended grouping explicit with parentheses.

## Proving they differ, by brute force

```js
function allCombinations() {
  const bools = [true, false];
  const combos = [];
  for (const a of bools) {
    for (const l of bools) {
      for (const o of bools) {
        combos.push([a, l, o]);
      }
    }
  }
  return combos;
}

for (const [isAdmin, isLoggedIn, isOwner] of allCombinations()) {
  const buggy = canEditBuggy(isAdmin, isLoggedIn, isOwner);
  const fixed = canEditFixed(isAdmin, isLoggedIn, isOwner);
  if (buggy !== fixed) {
    console.log({ isAdmin, isLoggedIn, isOwner, buggy, fixed });
  }
}
// { isAdmin: true, isLoggedIn: true,  isOwner: true,  buggy: true, fixed: false }
// { isAdmin: true, isLoggedIn: false, isOwner: true,  buggy: true, fixed: false }
```

Both disagreements happen exactly when `isAdmin` is `true` and
`isOwner` is `true` — an admin who owns the document. `canEditBuggy`
returns `true` (edit allowed) because `isOwner` alone satisfies the
`||`, regardless of `isAdmin`. `canEditFixed` returns `false`, matching
the spec: an admin should never be allowed to edit, full stop. This is
the exact bug the security review found — enumerating all eight
combinations instead of testing a couple by hand is what makes it
provable rather than just plausible.

<Checkpoint question="The brute-force loop above found exactly two combinations where canEditBuggy and canEditFixed disagree, both with isAdmin: true and isOwner: true. Why didn't a version with isAdmin: true, isLoggedIn: true, isOwner: false also disagree?">

Because in that row `isOwner` is `false`, so the `|| isOwner` in
`canEditBuggy` contributes nothing — the result falls back to
`!isAdmin && isLoggedIn`, which is `false && true`, i.e. `false`. That's
the same answer `canEditFixed` gives for that row. The bug only shows up
when `isOwner` is `true`, because that's the only case where the buggy
grouping's `|| isOwner` actually overrides the `!isAdmin` veto — with
`isOwner` false, both versions fall back to evaluating the `&&` the same
way, so they happen to agree even though the code is still wrong in
general.

</Checkpoint>

## Building the negation with De Morgan's laws

```js
function cannotEdit(isAdmin, isLoggedIn, isOwner) {
  // negating canEditFixed: !(!isAdmin && (isLoggedIn || isOwner))
  // step 1 (negate the &&):  isAdmin || !(isLoggedIn || isOwner)
  // step 2 (negate the ||):  isAdmin || (!isLoggedIn && !isOwner)
  return isAdmin || (!isLoggedIn && !isOwner);
}

for (const [isAdmin, isLoggedIn, isOwner] of allCombinations()) {
  const matches =
    cannotEdit(isAdmin, isLoggedIn, isOwner) ===
    !canEditFixed(isAdmin, isLoggedIn, isOwner);
  if (!matches) console.log("MISMATCH", { isAdmin, isLoggedIn, isOwner });
}
// (nothing logged — cannotEdit matches !canEditFixed for every combination)
```

Each De Morgan step flips exactly one operator: negating an `&&`
produces an `||` of negated pieces, and negating that inner `||`
produces an `&&` of negated pieces. Deriving it mechanically, one step
at a time, is what makes `cannotEdit` provably the exact opposite of
`canEditFixed` — not just "probably the opposite" from rewriting the
sentence in your head.

<Checkpoint question="cannotEdit was derived by negating canEditFixed in two De Morgan steps: first negating the outer &&, then negating the inner ||. Why does the derivation have to work from the outside in, rather than negating the inner || first?">

Because `!isAdmin && (isLoggedIn || isOwner)` is structured as an `&&`
of two pieces — `!isAdmin` and `(isLoggedIn || isOwner)` — and De
Morgan's law for negating an `&&` is the rule that applies to the
_whole_ expression first: `!(A && B)` becomes `!A || !B`. Only after
that outer step produces `isAdmin || !(isLoggedIn || isOwner)` does the
inner `!(isLoggedIn || isOwner)` become a standalone thing to negate on
its own, at which point the second De Morgan rule (for `||`) applies to
it. Trying to negate the inner `||` first would mean negating a piece
that isn't actually negated yet in the original expression — the `!`
in `cannotEdit` starts outside everything, so the derivation has to peel
off structure from the outside in, the same way you'd expand `-(a + b

- c)` from the outermost operation inward rather than the innermost.

</Checkpoint>

## Extend it: what if a careless negation skips the operator flip?

**What would go wrong if someone negated `canEditFixed` by just adding
`!` in front of each variable, without flipping the operators —
`!isAdmin && (!isLoggedIn && !isOwner)`?** Try it against `allCombinations()`
the same way `cannotEdit` was checked above: does it match
`!canEditFixed(...)` for every combination, or only some? **What about
a fourth field — say `isSuspended` — added to the original condition
with another `&&`: does the two-step De Morgan derivation above still
work if you have to negate three chained conditions instead of two,
and what changes?**

One quick check shows the careless version is not the true opposite:
when `isAdmin` is `true`, the real `cannotEdit` should be `true`, but
`!isAdmin && (!isLoggedIn && !isOwner)` starts with `false && ...`, so it
answers `false`. That is enough to prove the careless negation is wrong
before checking the remaining rows.

## Failure modes

| Failure mode                                                            | What it gets wrong                                                                                  |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Reading a mixed AND/OR expression as matching a spoken "A and (B or C)" | AND binds tighter than OR, so it actually groups as "(A AND B) OR C"                                |
| Testing only a couple of input combinations by hand                     | The one combination where two versions diverge can be exactly the one nobody tried                  |
| Negating a compound condition by adding `!` without flipping operators  | De Morgan's laws require AND to become OR (or OR to become AND), not just each variable to negate   |
| Assuming two boolean expressions that "look equivalent" are equivalent  | Only a full truth table (or a proof) confirms equivalence for every input, not just the tested ones |
| Trusting short-circuit evaluation order to imply meaning                | Short-circuiting affects what gets _evaluated_, not what the final boolean _result_ is              |
