## Reproducing the bug: the legacy boolean-flag version

Before the code, the intended state-machine idea can be read as a table:

| Current state | Event     | Next state  |
| ------------- | --------- | ----------- |
| `idle`        | `START`   | `uploading` |
| `uploading`   | `PAUSE`   | `paused`    |
| `paused`      | `RESUME`  | `uploading` |
| `uploading`   | `SUCCESS` | `success`   |
| `uploading`   | `FAIL`    | `error`     |

The boolean version below does not have that table as its source of
truth. Each branch edits separate checkboxes and must remember to clean
up all the others.

```js
function createLegacyUploadState() {
  return {
    isUploading: false,
    isPaused: false,
    isSuccess: false,
    isError: false,
  };
}

function legacyHandleEvent(state, event) {
  const next = { ...state };
  if (event === "START") {
    next.isUploading = true;
  } else if (event === "PAUSE") {
    next.isPaused = true;
  } else if (event === "RESUME") {
    next.isPaused = false;
  } else if (event === "SUCCESS") {
    // bug: forgets to reset isUploading back to false
    next.isSuccess = true;
  } else if (event === "FAIL") {
    next.isUploading = false;
    next.isError = true;
  }
  return next;
}

let legacyState = createLegacyUploadState();
legacyState = legacyHandleEvent(legacyState, "START");
legacyState = legacyHandleEvent(legacyState, "SUCCESS");

console.log(legacyState);
// { isUploading: true, isPaused: false, isSuccess: true, isError: false }
```

Verified: after `START` then `SUCCESS`, `isUploading` and `isSuccess`
are **both `true`** — the exact impossible state from L1's bug report.
There is a second suspicious detail too: `PAUSE` sets `isPaused = true`
but leaves `isUploading` alone. If the intended paused row is "uploading
false, paused true," then this branch has the same style of bug: a
handler changed one flag and trusted the others to stay meaningful.
Nothing in `legacyHandleEvent` prevented this; the `SUCCESS` branch
simply didn't happen to reset a flag it should have. This is a single
missing line, in a function that otherwise looks completely
reasonable — which is exactly why it's easy to ship.

## The fix: a state machine with an explicit transition table

```js
const transitions = {
  idle: { START: "uploading" },
  uploading: {
    PAUSE: "paused",
    SUCCESS: "success",
    FAIL: "error",
    CANCEL: "cancelled",
  },
  paused: { RESUME: "uploading", CANCEL: "cancelled" },
  success: {},
  error: { START: "uploading" },
  cancelled: {},
};

function transition(state, event) {
  const nextState = transitions[state] && transitions[state][event];
  if (!nextState) {
    throw new Error(`Invalid transition: cannot ${event} from ${state}`);
  }
  return nextState;
}

let fsmState = "idle";
fsmState = transition(fsmState, "START");
console.log(fsmState); // "uploading"
fsmState = transition(fsmState, "SUCCESS");
console.log(fsmState); // "success"
```

Verified: running the identical `START, SUCCESS` sequence produces a
single state value, `"success"` — there is no `isUploading` variable
left dangling `true`, because there's no `isUploading` variable at
all. The bug isn't fixed by writing more careful code; it's fixed by
removing the category of mistake the transition table can't represent.

Read the table object aloud:

- If I am in `idle` and `START` happens, go to `uploading`.
- If I am in `uploading` and `SUCCESS` happens, go to `success`.
- If I am in `success`, there are no allowed next events.

The expression `transitions[state] && transitions[state][event]` is a
JavaScript way to ask, "does this row exist, and does this event have a
next state from that row?"

## The transition table also rejects genuinely invalid sequences

```js
try {
  transition("success", "PAUSE");
} catch (err) {
  console.log(err.message);
  // "Invalid transition: cannot PAUSE from success"
}
```

Verified: attempting `PAUSE` from `success` throws immediately, rather
than silently producing some new, undefined combination. Compare this
to the legacy version, where calling `legacyHandleEvent(state,
"PAUSE")` on an already-succeeded upload would happily set
`isPaused: true` right next to `isSuccess: true` — another impossible
combination the boolean version has no way to refuse.

## Full paths through the state machine

```js
// idle -> uploading -> paused -> uploading -> success
let s = "idle";
for (const event of ["START", "PAUSE", "RESUME", "SUCCESS"]) {
  s = transition(s, event);
}
console.log(s); // "success"

// retry after a failure: idle -> uploading -> error -> uploading
let retry = "idle";
retry = transition(retry, "START");
retry = transition(retry, "FAIL");
console.log(retry); // "error"
retry = transition(retry, "START");
console.log(retry); // "uploading"
```

Verified: the pause/resume path and the retry-after-failure path both
work exactly as the diagram in L2 describes — `error` isn't a dead
end, `START` from `error` is an explicit, defined transition back to
`uploading`.

## Extend it: what changes if a "retry limit" needs to be added?

**Suppose the real requirement is "allow retrying from `error` at most
2 times before moving to a new `permanently-failed` state." Can this
be expressed by adding states and transitions to the table above,
without going back to independent boolean flags (like adding a
`retryCount` boolean-style flag) to track it?** Try sketching the
additional states and transitions this would need — what has to change
about `transition`'s signature if the _next_ state depends on more
than just the current state and the event?

A guided sketch could model retry count as explicit states:

| Current state | Event   | Next state           |
| ------------- | ------- | -------------------- |
| `error-0`     | `START` | `uploading-1`        |
| `uploading-1` | `FAIL`  | `error-1`            |
| `error-1`     | `START` | `uploading-2`        |
| `uploading-2` | `FAIL`  | `permanently-failed` |

In a real implementation you might keep extra context such as
`retryCount` next to the state, but the warning is the same: do not let
that context silently create states the table never modeled.

## Failure modes

| Failure mode                                                                         | What it gets wrong                                                                                                                       |
| ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Adding "just one more boolean flag" to an existing ad hoc flag set                   | Each new flag doubles the total combination count — the meaningful-to-meaningless ratio only gets worse                                  |
| Assuming a missing `else` branch is a rare kind of bug                               | It's the _default_ failure mode of flag-based state — every handler has to remember every other flag, forever                            |
| Treating a state machine's rejected transition as a crash to work around             | A thrown/rejected invalid transition is the system correctly refusing an impossible request — the fix is the calling code, not the table |
| Believing a state diagram is just documentation, disconnected from the code          | In L3, the transition table _is_ the diagram — the code enforces exactly what the diagram claims, not a looser approximation of it       |
| Using a state machine but still allowing extra, un-modeled boolean flags on the side | Any flag outside the state machine reopens the same "independent combinations" problem the state machine was meant to close              |
