A developer writes a recursive function to compute the total size of
a folder, where a folder can contain files and other folders, nested
arbitrarily deep. To check it, they trace through a couple of example
trees by hand, following each recursive call until it feels right.
For a shallow example this works fine — but for a deeply nested,
realistic folder structure, tracing every call by hand quickly
becomes impossible to hold in your head. **The function ships because
the examples worked, not because there's an actual argument for why
it's correct on every possible input. Is there a way to get real
confidence here, without tracing every path by hand?**

</Scenario>

## Recursion in one sentence

A recursive function solves a big thing by asking the same function to
solve smaller pieces of that thing. For folders, that means "to know the
size of this folder, ask for the size of each child file or child
folder, then add those answers."

For a tiny no-code example:

| Item          | What it contains            | Total size   |
| ------------- | --------------------------- | ------------ |
| `photo.jpg`   | just itself                 | 4 MB         |
| `trip-folder` | `photo.jpg` + `map.pdf`     | 4 + 1 = 5 MB |
| `archive`     | `trip-folder` + `notes.txt` | 5 + 2 = 7 MB |

Tracing follows those steps for one concrete folder. Induction asks
whether the same reasoning works for every valid folder shape.

## The shape of the problem

- Manually **tracing** a recursive function means mentally following
  every call it makes, one level at a time — which works for a
  shallow example, but becomes unmanageable and error-prone as depth
  or branching grows, and never actually proves the function is
  correct for inputs you didn't trace.
- **Mathematical induction** offers a completely different kind of
  argument: instead of checking every case, you check a **base case**
  (the simplest possible input) and an **inductive step** (assuming
  the function is correct for smaller inputs, show it's correct for a
  bigger one built from them). If both hold, the function is correct
  for every valid, finite input that eventually reaches a base case,
  without tracing any of them individually.
- This isn't just a mathematician's formality — it's a genuinely
  practical way to reason about recursive code: it tells you exactly
  where to look when something's wrong (is the base case broken? is
  the inductive step's assumption violated?) instead of re-tracing
  the whole thing from scratch.

## Key terms

- **Base case** — the simplest input a recursive function handles
  directly, without calling itself again (e.g., a file, or an empty
  folder whose total size is `0`).
- **Inductive step** — the part of the reasoning (and usually the
  code) that assumes the recursive call already gives the correct
  answer for a smaller version of the problem, and shows how to build
  the correct answer for the current, larger input from that.
- **Inductive hypothesis** — the specific assumption made in the
  inductive step: "assume this works correctly for every input
  smaller than the one currently being handled."
- **Recursion trace** — a manual walkthrough of a recursive function's
  actual call sequence for one specific input, useful for debugging a
  particular case but not a substitute for a general correctness
  argument.

Note the overloaded word: this unit uses **mathematical induction**,
the base-case-plus-step proof pattern for recursive structures. That is
different from the everyday/probabilistic "inductive argument" in
`logic/formal-informal-logic`, where evidence makes a conclusion more
likely without proving it with certainty.

## What this unit covers

L2 works through the structure of an inductive argument and why it
scales to any depth in a way that hand-tracing never can. L3 applies
it directly to the Scenario's folder-size function, including finding
and diagnosing a genuine bug using the induction structure itself —
not by re-tracing, but by asking specifically which part of the
argument the bug actually violates.
