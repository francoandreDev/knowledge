A shipping-cost function has three price tiers: under 5kg, 5–10kg,
and over 10kg. The developer writes three tests — one weight
comfortably inside each tier — and all three pass. The function
ships. A week later, a customer's package weighs exactly 5.0kg and
gets charged the middle tier's price instead of the cheap tier's,
because the business rule says "5kg and under" but the code checks
`weight < 5`. **Every test the developer wrote passed. The bug was
real. What kind of input does "pick one value from each case" never
actually test — and how would you have found this one before a
customer did?**

## Tiny programming glossary

| Term       | Plain meaning in this unit                                      |
| ---------- | --------------------------------------------------------------- |
| Function   | A rule that receives an input and returns an output             |
| Input      | The value you give the rule, like `weight = 5.0`                |
| Output     | The answer the rule gives back, like a shipping price           |
| Test       | A checked example: "for this input, I expect this output"       |
| Comparison | A question such as "less than 5?" or "less than or equal to 5?" |
| `<`        | Less than; `weight < 5` does **not** include exactly `5`        |
| `<=`       | Less than or equal; `weight <= 5` **does** include exactly `5`  |

## The shape of the problem

- Choosing one test value "from" each tier tests the _interior_ of
  each case, never the _edges_ between them — and the edges are
  exactly where an author's mental model (`< 5`) and the actual
  business rule ("5 and under") most often silently diverge.
- Off-by-one mistakes (`<` vs. `<=`, `>` vs. `>=`) are invisible from
  the interior of a range — `4.99` and `5.01` behave identically to
  `<` and `<=`; only the exact boundary value tells the two apart.
- Testing every specific value is impossible for most functions —
  the fix isn't "test more values," it's **reasoning about the
  structure of the input space**: which values are boundaries,
  which behaviors should hold across _every_ input (not just the
  ones tested), and which specific values are worth checking by name.

Input space just means "the set of values the function might receive."
For shipping, that means weights: `0`, `2`, `4.99`, `5.0`, `5.01`,
`10`, very large weights, and invalid values like negative weight or a
missing weight.

| Value | Where it sits           | Business rule says | Buggy `< 5` code says |
| ----- | ----------------------- | ------------------ | --------------------- |
| 4.99  | Just below the boundary | Cheap tier         | Cheap tier            |
| 5.00  | Exactly on the boundary | Cheap tier         | Middle tier           |
| 5.01  | Just above the boundary | Middle tier        | Middle tier           |

## Key terms

- **Edge case** — an input at the extreme or unusual end of what a
  function accepts: empty, zero, negative, maximum, exactly on a
  threshold — as opposed to a "typical" input from the interior of a
  range.
- **Boundary condition** — the specific point where a function's
  behavior is supposed to change (a price tier threshold, an array's
  first/last index, a loop's start/end) — the single most common
  place an edge-case bug hides.
- **Equivalence class** — a group of inputs a function is expected to
  treat the same way (e.g. "all weights strictly between 0 and 5kg
  behave identically") — testing one representative value per class
  is efficient, _if_ the classes and their boundaries are identified
  correctly.
- **Valid input** — a value the function is supposed to accept. A
  positive weight is valid; a missing weight or text like `"five"` may
  be invalid unless another part of the system converts it first.
- **Invariant** — a property that should hold true across _every_
  valid input, not just specific examples (e.g. "shipping cost never
  decreases as weight increases") — useful for catching bugs example
  tests don't happen to hit, though not every bug violates an
  invariant that's easy to state.
- **Off-by-one error** — a boundary condition using the wrong
  comparison (`<` instead of `<=`, or an index shifted by one),
  producing incorrect behavior only exactly at the boundary.

## What this unit covers

L2 works through how to systematically find the boundaries and
equivalence classes of a function's input space instead of guessing
at "a few more test cases," plus what invariants can and can't catch
on their own. L3 reproduces the shipping-cost bug in real code,
demonstrates that a plausible-sounding invariant check (monotonicity)
does _not_ catch this particular bug, and builds the boundary-value
test suite that does — closing with a question about which category
of edge case invariant-checking is naturally suited to, and which
category boundary-value analysis is needed for instead.
