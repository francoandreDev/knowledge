## What does the buggy code actually do?

**Why did the developer's three tests pass?** Here is the rule in words, then in
code:

```text
Reject a negative weight.
If weight is less than 5, charge 4.99.
If weight is less than 10, charge 8.99.
Otherwise charge 14.99.
```

```js
function shippingCostBuggy(weightKg) {
  if (weightKg < 0) throw new Error("weight cannot be negative");
  if (weightKg < 5) return 4.99;
  if (weightKg < 10) return 8.99;
  return 14.99;
}
```

Running it on the original tests and the lines gives:

| Call                    | Rule expects | Buggy returns | Result    |
| ----------------------- | ------------ | ------------- | --------- |
| `shippingCostBuggy(2)`  | 4.99         | 4.99          | ok        |
| `shippingCostBuggy(5)`  | 4.99         | 8.99          | **wrong** |
| `shippingCostBuggy(6)`  | 8.99         | 8.99          | ok        |
| `shippingCostBuggy(10)` | 8.99         | 14.99         | **wrong** |
| `shippingCostBuggy(15)` | 14.99        | 14.99         | ok        |

`weightKg < 5` asks "strictly below 5?". For exactly 5.0 the answer is no, so
control falls through to the next rule. That fall-through is the whole bug.

<Checkpoint question="The three original tests (2, 6, 15) all passed. What single property do they share that let the bug through?">

All three are interior values, comfortably inside their band and nowhere near a
line. None can tell `< 5` from `<= 5`, because both comparisons return the same
answer for them. Adding more interior values would not change that: the bug's
whole footprint is the line itself.

</Checkpoint>

## What happens when the invariant runs?

**Will "price never decreases" flag the buggy function?** Run it instead of
assuming:

```js
function checkMonotonic(fn, maxWeight, step) {
  let prev = fn(0);
  for (let w = step; w <= maxWeight; w += step) {
    const cur = fn(w);
    if (cur < prev) return { violated: true, at: w, prev, cur };
    prev = cur;
  }
  return { violated: false };
}

checkMonotonic(shippingCostBuggy, 20, 0.5);
// { violated: false }  the bug passes straight through
```

The helper walks 0 to 20 kg in half-kilo steps and asks one question: did the
price ever go down? On the buggy code it never does, because 5.0 jumping up to
8.99 is still going up. The invariant is well written; it is simply not sensitive
to this kind of bug. Tested against a different bug (the middle band priced at
3.99), the same helper reports a violation at 5.5 kg.

| Check                      | Buggy `< 5`   | Middle band priced 3.99 |
| -------------------------- | ------------- | ----------------------- |
| Monotonic sweep 0 to 20 kg | passes (miss) | **fails at 5.5 kg**     |
| Boundary test at 5.0       | **fails**     | passes                  |

The two checks catch opposite bugs, which is why one cannot replace the other.

## The suite that catches it

**Which inputs would have exposed it?** The line plus a step on each side, per L2:

```js
function shippingCost(weightKg) {
  if (weightKg < 0) throw new Error("weight cannot be negative");
  if (weightKg <= 5) return 4.99;
  if (weightKg <= 10) return 8.99;
  return 14.99;
}

// 4.99 -> 4.99, 5.0 -> 4.99, 5.01 -> 8.99
// 9.99 -> 8.99, 10.0 -> 8.99, 10.01 -> 14.99
```

Against `shippingCostBuggy`, the calls at 5.0 and 10.0 return one tier too high.
Against `shippingCost`, all six match the rule.

The domain checks are a different category from the lines. They test the
function's assumptions rather than its thresholds:

```js
shippingCost(0); // 4.99, zero is valid and sits in the cheap band
shippingCost(-0.01); // throws "weight cannot be negative"
```

A complete suite needs both groups. Line tests would never have noticed a missing
negative-weight check, and a negative-weight check would never have noticed the
5.0 bug.

## This is one case, not the whole territory

The process (split the input space, find the lines, test each line and a step on
both sides, test the assumed domain) carries over to date ranges, discount tiers,
pagination limits and retry counts. What is specific to the worked example is its
size: two lines, easy to list by hand. A tax table with seven brackets has more
lines, and reading the actual conditionals matters more than guessing.

**Try extending it yourself.** Suppose a fourth tier is added for packages over
50 kg that charges a per-kg surcharge instead of a flat price. Do the tests at 5
and 10 still cover the risk? A rate change is a different kind of boundary from a
price change: which new invariant (for example, the price at 50.01 kg is only a
few cents above the price at 50 kg) would you add, and what bug would it catch
that the line tests would not?

## Failure modes

| Failure mode                                            | What it gets wrong                                                                |
| ------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Treating a passing invariant as proof of correct bands  | Monotonicity holds even when a weight sits in the wrong band                      |
| Testing only the exact line, not a step on each side    | A single point can pass by coincidence; the comparison shows only across the line |
| Swapping boundary tests for invariants (or the reverse) | They catch different bug families; dropping either leaves a blind spot            |
| Choosing "realistic" test data                          | Realistic values cluster in the interior, exactly where the bug is not            |
