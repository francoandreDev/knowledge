A platform team maintains a spreadsheet: one row per service, one column
listing what it "needs" before it can start. Service `billing` needs
`accounts` and `ledger`. `ledger` needs `accounts`. Whenever someone adds
a service, they read down the column, eyeball what looks safe, and ship
it. For six months this works — until a deploy hangs forever, and
someone finally traces it by hand: `accounts` needs `audit-log`,
`audit-log` needs `billing`, and `billing` needs `accounts`. A circular
dependency, three hops long, sitting in that spreadsheet since the third
row was ever added. Nobody was careless — the column was accurate the
whole time. **What changed between "accurate spreadsheet, invisible
cycle" and "same facts, cycle caught in one script run"?**

Nothing about the underlying services changed. What changed was the
_representation_: the same 14 rows, treated as nodes and edges of a
directed graph, let a short, well-known algorithm — walk every path,
watch for a node you've already visited on the current path — find in
milliseconds what six months of careful reading never surfaced.

## The shape of the problem

A **formal model** (or **abstraction**) is a deliberately simplified,
precisely defined stand-in for a messy real situation — one that keeps
only the properties that matter for the question being asked and
throws away everything else. The spreadsheet already had all the raw
facts. It just had no _structure_ that a human, or a program, could
mechanically check for cycles, dependency depth, or safe deploy order.
A directed graph is a structure with well-known algorithms already
built for exactly those questions.

This unit builds on `problem-decomposition` — breaking a vague ask into
concrete, attackable pieces — but goes one step further: once the
pieces exist, _what shape do you give each one_ so that reasoning about
it stops being ad hoc? `state-machines` is one specific answer to that
question (model a thing-with-a-lifecycle as named states and legal
transitions). This unit is about the general skill: recognizing which
formal shape a given messy problem actually calls for, of which state
machines are one instance among several.

## Formal structures and what they're good at

| Real-world problem shape                                                   | Formal structure                         | What it unlocks                                                 |
| -------------------------------------------------------------------------- | ---------------------------------------- | --------------------------------------------------------------- |
| "X needs/depends on/links to Y"                                            | Graph (nodes + edges)                    | Reachability, cycle detection, shortest path, topological order |
| "A thing moves through named phases with rules about what can follow what" | State machine (states + transitions)     | Impossible-state elimination, exhaustive transition checking    |
| "Fit these things together under limits (time, space, people)"             | Constraint set (variables + constraints) | Solvers can find a valid assignment, or prove none exists       |
| "If condition X holds, then Y must hold"                                   | Mathematical relation / rule set         | Consistency checking, deriving consequences automatically       |

Each row trades a specific kind of mess for a specific kind of tool.
The spreadsheet's mess was relationships between things — a graph
converts that mess into an algorithm. A messy approval workflow's mess
is "what can happen next" — a state machine converts that into a
transition table a computer can validate exhaustively. Choosing badly
(forcing a cyclic web into a strict tree, say) throws the unlock away
and can make an easy problem hard again — L3 works through exactly
that failure mode.

## Key terms

- **Abstraction / formal model** — a simplified, precisely defined
  representation of a real situation that keeps only the properties
  relevant to the question being asked.
- **Graph** — a set of nodes and directed or undirected edges between
  them, used to model relationships, dependencies, or connections.
- **Cycle** — a path through a graph that returns to a node already on
  that path; in a dependency graph, a cycle means "nothing in the loop
  can ever be the first one ready."
- **State machine** — a formal model of a finite set of named states
  and the legal transitions between them (covered in depth in
  `state-machines`).
- **Constraint set** — a formal model expressing a problem as
  variables and the rules (constraints) they must jointly satisfy.
- **Over-abstraction** — a model detailed enough to be technically
  accurate but too complex to reason about or use, defeating the
  point of simplifying in the first place.
- **Under-abstraction** — a model too coarse to capture the property
  the question actually depends on, so it answers a different,
  easier question than the one that was asked.
