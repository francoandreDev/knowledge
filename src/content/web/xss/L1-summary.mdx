A comment section renders user-submitted text directly into the
page. Someone submits a "comment" that's actually a `<script>` tag
instead of ordinary text. Every other visitor who views that page has
this script execute in their own browser — with their own logged-in
session — silently sending their session cookie to a server the
attacker controls. **The attacker never touched any other user's
account directly. So how did they gain access to other people's
sessions just by submitting a comment?**

## Before the security terms

| Idea           | Plain meaning                                                             |
| -------------- | ------------------------------------------------------------------------- |
| Browser        | The program running the page for the user                                 |
| Server         | The machine/app that sends the page and receives requests                 |
| Session        | The site's way of remembering "this browser is logged in as this user"    |
| Session cookie | A small credential the browser automatically sends back to that same site |
| Text vs. code  | Text should be displayed; code is instructions the browser may execute    |

XSS is dangerous because the malicious code runs inside the victim's own
browser, on the vulnerable site. From the site's point of view, requests
made by that script can look like they came from the victim's legitimate
session.

## The shape of the problem

- **Cross-site scripting (XSS)** happens when a page renders
  user-supplied input as if it were trusted code, letting an
  attacker's script execute in another user's browser, in that
  user's own authenticated context — as if the attacker were running
  code with the victim's own login session.
- XSS is a genuinely different threat from **cross-site request
  forgery (CSRF)**, which tricks a victim's browser into making an
  unwanted authenticated request (not into running arbitrary
  attacker-controlled code) — the two require different defenses,
  and confusing them leads to solving the wrong problem.
- **Sanitization** (the broad goal: user input must stay data, never
  become code) and **escaping/output encoding** (the concrete rendering
  move this unit implements: convert HTML-control characters into safe
  text) prevent the injection in the first place. **Content Security
  Policy (CSP)** is a separate browser-level policy restricting what
  scripts are allowed to run at all, limiting damage if an injection
  somehow still gets through.

## Key terms

- **XSS (cross-site scripting)** — injecting attacker-controlled
  script into a page so it executes in another user's browser, in
  that user's own session.
- **CSRF (cross-site request forgery)** — tricking a victim's already
  logged-in browser into submitting a request the victim didn't
  intend, exploiting the fact that the browser automatically attaches
  the victim's credentials.
- **Sanitization / escaping** — ensuring user-supplied content is
  treated as inert data when rendered into a page. In this unit, the
  concrete technique is escaping HTML-control characters before output.
- **Content Security Policy (CSP)** — an HTTP header that tells the
  browser which sources of scripts, styles, and other resources are
  allowed to load and execute on a page, restricting what an injected
  script could do even if one gets through.

## What this unit covers

L2 works through why XSS and CSRF need genuinely different defenses
despite both being described as "malicious input" problems, and how
sanitization and CSP work as independent, stacked layers rather than
substitutes for each other. L3 implements the Scenario's vulnerable
comment renderer, the actual exploit, the sanitization fix, and a CSP
policy as a second layer of defense.
