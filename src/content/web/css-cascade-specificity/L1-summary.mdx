A developer adds one line of CSS — `.btn-primary { background: blue; }` — at the very
bottom of the stylesheet, certain that "last one written wins." The button stays gray.
Nothing in the browser is broken; the CSS is valid; there's no error anywhere. The rule
simply never had a chance: an older, more specific rule (`#page .toolbar .btn`) was
always going to beat it, regardless of which one was written more recently.

| Rule                           | Written             | Applies? |
| ------------------------------ | ------------------- | -------- |
| `#page .toolbar .btn { gray }` | Months ago          | ✅ Yes   |
| `.btn-primary { blue }`        | Just now, last line | ❌ No    |

**Both rules target the same button. Why does the older one win?**

## The tiny CSS vocabulary this depends on

CSS is written as rules. A rule has a **selector** that finds elements, and
one or more **declarations** that say what visual property should change:

```css
.btn-primary {
  background: blue;
}
```

Here `.btn-primary` is a selector, `background: blue` is a declaration,
`background` is the property, and `blue` is the value. A selector that starts
with `.` looks for a class, like `<button class="btn-primary">`. A selector
that starts with `#` looks for an id, like `<main id="page">`.

Reusable styling usually starts with a small class that can be placed on many
elements:

```html
<button class="btn">Save</button>
<a class="btn" href="/pricing">See pricing</a>
<button class="btn btn-primary">Buy now</button>
```

The hard part is not writing one reusable class. The hard part is keeping old,
more specific selectors from overpowering that reusable class everywhere it is
used.

- The browser doesn't apply CSS rules in "whichever was written last" order — it resolves every rule that matches an element through the **cascade**, which decides a winner using three factors, checked in this exact priority: **origin & importance** (where the rule came from, and whether it's marked `!important`), then **specificity** (how precisely the selector targets the element), then **source order** (last one wins — but only as the final tiebreaker, after the first two are exhausted).
- **Specificity is a score computed from the selector itself**, not from when or where in the file it appears. The common mental model: count IDs, classes/attributes/pseudo-classes, and elements/pseudo-elements in the selector, then compare in that order — an ID selector alone (`#page`) already outranks any number of classes, because ID beats class before class-count is even considered.
- This is exactly what happened above: `#page .toolbar .btn` has 1 id + 2 classes; `.btn-primary` has 1 class. The id alone puts the first rule ahead — source order never even gets consulted, because specificity already produced a winner.
- **Inheritance is a separate mechanism from the cascade** — some properties (`color`, `font-family`, `line-height`) pass down from parent to child automatically if nothing overrides them; others (`border`, `padding`, `background`) don't inherit at all, regardless of specificity. Confusing "it inherited" with "it cascaded" is a common source of CSS debugging confusion.
- **`!important` doesn't fix a specificity loss — it escalates the fight to a different, harder-to-track battlefield.** A declaration marked `!important` jumps to the front of the origin-and-importance check, ahead of specificity entirely — which means the only thing that can override it later is another `!important` declaration that wins on origin or specificity among `!important` rules. Reaching for `!important` to win one battle routinely starts an arms race that makes every future style change riskier.
- The practical skill this unit builds: before adding a CSS rule expecting it to apply, compare its specificity (and origin/importance) against whatever's already targeting that element — not just check whether it comes later in the file.

## Specificity at a glance

| Selector example      | IDs | Classes/attrs/pseudo-classes | Elements/pseudo-elements | Beats                                                                                                    |
| --------------------- | --- | ---------------------------- | ------------------------ | -------------------------------------------------------------------------------------------------------- |
| `#page .toolbar .btn` | 1   | 2                            | 0                        | Any selector with 0 ids                                                                                  |
| `.btn-primary`        | 0   | 1                            | 0                        | `a`, `button`, `div`                                                                                     |
| `button.btn`          | 0   | 1                            | 1                        | `.btn-primary` (ids tie at 0, classes tie at 1, so the element count breaks the tie — `button.btn` wins) |
| `div p a:hover`       | 0   | 1                            | 3                        | `a` alone                                                                                                |
| inline `style="..."`  | —   | —                            | —                        | Every selector above (origin outranks specificity entirely)                                              |
