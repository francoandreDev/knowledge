A contact list renders 5,000 rows. Deleting one contact from the
middle should mean removing exactly one row — every other contact is
still the same person, in the same order, one slot earlier. Instead,
the UI visibly redraws thousands of rows, and the page briefly stutters.
**Only one contact was actually removed. So why does the screen behave
as if almost every row changed?**

## The shape of the problem

- Modern UI frameworks don't touch the real DOM directly on every
  change — they compute a lightweight in-memory description of what
  the UI should look like (a **virtual DOM**), compare it to the
  previous version (**diffing**), and apply only the specific changes
  needed to the real DOM.
- Diffing a list of items requires deciding what makes two items "the
  same" between renders. Comparing by **position** (item 3 is item 3,
  whatever it is now) is very different from comparing by **identity**
  (item with id 47 is still item id 47, wherever it now sits in the
  list) — and choosing wrong turns a one-item change into a
  near-total rewrite.
- Every real DOM change the browser applies can trigger **reflow**
  (recalculating layout — positions and sizes of elements) and
  **repaint** (redrawing pixels) — expensive work that scales with how
  much of the page actually changed, not with how much data logically
  changed.

## Key terms

- **Virtual DOM** — an in-memory, lightweight representation of what
  the UI should currently look like, compared against the previous
  version to compute the minimal real DOM changes needed.
- **Diffing (reconciliation)** — the process of comparing an old and
  new virtual DOM tree to determine exactly what changed.
- **Key** — a stable identifier attached to each item in a rendered
  list, used during diffing to match an item in the new list back to
  the same item in the old list, regardless of position.
- **Reflow / repaint** — reflow is the browser recalculating element
  positions and sizes after a layout-affecting change; repaint is
  redrawing the resulting pixels. Both cost real time proportional to
  how much of the page is affected.

## What this unit covers

L2 works through why position-based diffing turns a small logical
change into a large set of real DOM operations, and what the browser's
rendering pipeline actually does with each of those operations. L3
implements both a position-based ("unkeyed") and identity-based
("keyed") diff function, measures the actual number of DOM operations
each produces for the Scenario's exact case, and shows how dramatically
that gap grows as the list scales.
