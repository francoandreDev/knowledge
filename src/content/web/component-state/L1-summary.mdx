## The shape of the problem

- Each place on the page that displays a piece of state (like the cart
  count) is only correct if the code path that changes that state
  remembers to update it — and every new place a value is added to a
  page is one more place that can be forgotten.
- The bug above isn't a typo — it's a structural problem: the "quick
  buy" button's click handler updates the drawer badge directly but was
  never told about the header badge, because nothing forces every
  state-changing action to route through every place that displays it.
- The fix isn't "remember better" — it's changing the structure so
  there's exactly one place state lives and exactly one path from a
  change to every display of it, so forgetting isn't possible.

## Key terms

- **State** — the data that determines what a page currently shows,
  which can change over time in response to user actions (like a cart
  count, a form's input value, or whether a menu is open).
- **Component state** — state that belongs to one part of the UI, such
  as one menu being open or one input's current text. It should stay
  local while only that component needs it, and only move outward when
  multiple components need to read or change it.
- **Single source of truth** — keeping exactly one authoritative copy
  of a piece of state, so every display of it reads from the same
  place instead of keeping its own separate, driftable copy.
- **Unidirectional data flow** — a discipline where state only changes
  through one defined path (an action updates the state, then the
  state update triggers re-rendering everything that depends on it) —
  rather than code reaching in and mutating the display directly from
  many different places.
- **Render function** — code that takes the current state and produces
  what the page should show, run every time the state changes, instead
  of being run inconsistently by whichever handler happens to remember to call it.

No global chaos does **not** mean putting every value in one giant global
object. It means each shared value has one clear owner: local if one component
uses it, lifted to a common owner if several nearby components use it, or held
in a focused store if distant parts of the page need the same value.

## What this unit covers

L2 works through why direct, scattered DOM updates are what causes
this class of bug, and what unidirectional data flow looks like as a
loop: action → state update → render. L3 reproduces the two-badge bug
with real, runnable code, then fixes it by routing every update through
a single store that every display subscribes to.
