## A real dependency-graph resolver

Before the code, trace the first example by hand:

1. Start at `app`, because it is the entry point.
2. `app` needs `utils`, so visit `utils` first.
3. `utils` needs nothing, so add `utils` to the output.
4. Back at `app`, now visit `api`.
5. `api` also needs `utils`, but `utils` is already included, so skip it.
6. Add `api`, then finally add `app`.

That human trace is exactly what the function below automates: never output a
file until its dependencies have already been handled, and never output the
same file twice.

```js
// resolve-order.mjs
function resolveOrder(graph) {
  const visited = new Set();
  const order = [];

  function visit(node) {
    if (visited.has(node)) return; // already included — this is what prevents duplicates
    visited.add(node);
    for (const dep of graph[node] || []) visit(dep);
    order.push(node); // a module is only added AFTER all its dependencies are
  }

  for (const node in graph) visit(node);
  return order;
}

const graph = { app: ["utils", "api"], utils: [], api: ["utils"] };
console.log(resolveOrder(graph));
// [ 'utils', 'api', 'app' ]
```

This is a real topological sort: `visit` only appends a module to
`order` after recursively visiting everything it depends on, which
guarantees every dependency appears before the thing that needs it —
`utils` before `api`, and both before `app`, exactly matching what the
opening scenario's manually-ordered script tags failed to guarantee.

## The shared-dependency case, resolved once

```js
const graph2 = { main: ["a", "b"], a: ["c"], b: ["c"], c: [] };
console.log(resolveOrder(graph2));
// [ 'c', 'a', 'b', 'main' ]
```

Both `a` and `b` depend on `c`, but `c` appears **exactly once** in the
output — the `visited` set is what makes this happen: the first time
`visit("c")` runs (while resolving `a`'s dependencies), `c` gets added
to `order` and marked visited; when `b`'s dependency on `c` is
processed next, `visit("c")` returns immediately without adding a
second copy. A hand-maintained set of script tags has no equivalent
safeguard — nothing stops `c.js` from being pasted in twice, or from
being left out because whoever added `b.js` assumed someone else had
already included it.

<Checkpoint question="Given graph2 = { main: ['a', 'b'], a: ['c'], b: ['c'], c: [] }, walk through what happens when visit('b') runs after visit('a') has already fully completed. Does visit('c') run again inside visit('b'), and does 'c' get pushed to order a second time?">

`visit("c")` does run again — the function is still called, because `b`'s
dependency list still names `c`. But the very first line of `visit` checks
`visited.has(node)` before doing anything else, and `c` was already added to
`visited` while resolving `a`. So the call returns immediately: it never
reaches the loop over `graph[node]`, and it never reaches the
`order.push(node)` line. `order` only gets a new entry for `c` the first
time `visit("c")` runs to completion; every later call is a no-op guard
check. That's the whole mechanism — not a special case for duplicates, just
the same early-return check running again.

## What a naive, unresolved order actually breaks

**If `Object.keys(graph)` is a one-line way to list a graph's modules,
why not just use that as the output order instead of writing a
resolver at all?** Because `Object.keys` reflects insertion order —
whatever sequence the properties happened to be written in — which has
no required relationship to actual dependencies. For
`{ app: ["utils", "api"], utils: [], api: ["utils"] }`, the two orders
diverge exactly where it matters:

| Order                     | Result                    | Why                                                                       |
| ------------------------- | ------------------------- | ------------------------------------------------------------------------- |
| Naive (`Object.keys`)     | `['app', 'utils', 'api']` | Insertion order — `app` was simply written first in the object            |
| Resolved (`resolveOrder`) | `['utils', 'api', 'app']` | Walks the actual edges — a dependency is never placed after its dependent |

The naive order places `app` first — exactly the bug from the opening
scenario, where a script needing `utils` loads before `utils.js` has
run. That relationship only comes from actually walking the graph's
edges, which is what `resolveOrder` does and a plain list of script
tags never does.

## Tree-shaking: using the same graph information one step further

**Does finding unused exports need a new kind of analysis, separate
from the graph that already computed build order?** No — it's the same
import information, read for a different question. Given
`allExports = ["formatDate", "formatCurrency", "debounce", "throttle"]`
and `usedImports = ["formatDate", "debounce"]` (everything actually
imported anywhere in the graph), the unused ones are simply whatever's
left over:

| Export           | Imported anywhere in the graph? | Safe to drop from the bundle? |
| ---------------- | ------------------------------- | ----------------------------- |
| `formatDate`     | Yes                             | No                            |
| `debounce`       | Yes                             | No                            |
| `formatCurrency` | No                              | Yes                           |
| `throttle`       | No                              | Yes                           |

The same dependency information that makes correct ordering possible
also makes this possible: since the bundler already knows exactly
which exports are imported anywhere in the graph, it can safely
exclude `formatCurrency` and `throttle` from the final bundle — nobody
in the entire dependency graph asked for them. This is only safe
because the graph is exhaustive; a build tool with no visibility into
every importer has no way to be sure an export is really unused
anywhere.

<Checkpoint question="findUnusedExports only compared allExports against usedImports gathered from the whole graph. If a project used dynamic access like moduleObject['format' + suffix] somewhere instead of a plain 'import { formatCurrency }' statement, would tree-shaking still safely know formatCurrency is used?">

No — and that is exactly why the failure-modes table below flags dynamic
access as a real risk. Tree-shaking's safety depends on the bundler being
able to statically read every import statement while walking the graph;
`"import { formatCurrency }"` is something it can see and record in
`usedImports` directly from the source text. `moduleObject['format' +
suffix]` builds the property name at runtime — the bundler has no way to
evaluate `suffix` while just reading the file, so it cannot know whether
`formatCurrency` ends up referenced or not. Faced with that uncertainty, a
safe bundler has to either keep the export anyway or risk removing
something a live code path still needs — the same graph-completeness
guarantee that makes tree-shaking safe for static imports simply doesn't
extend to dynamically-computed ones.

## Extend it: what if two modules import each other?

**Everything above assumed the graph has no cycles. What happens if
`a.js` imports something from `b.js`, and `b.js` also imports something
from `a.js`?** `resolveOrder`'s `visited` check prevents an infinite
loop either way — try `resolveOrder({ a: ["b"], b: ["a"] })` and it
terminates, returning `['b', 'a']` rather than recursing forever. But
termination isn't the same as correctness: whichever module gets
visited _first_ ends up executed while the other one hasn't fully run
yet, meaning anything the not-yet-run module was supposed to export
may not exist yet at the moment the first module needs it. Real
bundlers handle this without crashing, but a circular import often
signals a design problem worth fixing directly — usually by extracting
whatever both files need into a third, shared module neither depends
on the other for.

## Failure modes

| Failure mode                                                   | What it gets wrong                                                                                                                                                         |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Maintaining script-tag order by hand as a codebase grows       | Nothing enforces the order stays correct as dependencies change — it silently breaks the next time someone adds or reorders a file                                         |
| Assuming a shared file included by two script tags is harmless | Either duplicates the file's code and global state, or silently relies on one copy loading first with no guarantee it does                                                 |
| Treating tree-shaking as automatic regardless of code style    | It depends on the bundler being able to statically see what's actually imported — dynamic `require()`-style access can hide usage a bundler can't verify is safe to remove |
| Assuming bundling and transpilation are the same problem       | Bundling combines files correctly; transpilation rewrites syntax for compatibility — a project can need one without needing the other                                      |
| Introducing a circular import without noticing                 | The graph resolver won't crash, but the two modules can end up executing in an order where one isn't fully initialized when the other needs it                             |
