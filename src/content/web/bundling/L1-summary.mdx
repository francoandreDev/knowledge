A page loads four JavaScript files with plain `<script>` tags, in a
specific order someone worked out by trial and error months ago. A new
shared utility file needs to be added, so it gets pasted in as a fifth
tag — after the others, since that seems like the safe place to add
something new. The page immediately breaks: `utils is not defined`,
even though `utils.js` is right there in the page's source.
**`utils.js` is loading. The browser is executing it. So why does the
code that needs it say it doesn't exist?**

</Scenario>

## The shape of the problem

- Plain `<script>` tags execute in the exact order they appear on the
  page, top to bottom — nothing checks whether a script placed earlier
  actually needs something defined by a script placed later.
- As a codebase grows past a handful of files, keeping every file's
  script tag in the one correct order by hand stops being a minor
  chore and starts being a real, recurring source of bugs — and that's
  before considering that most browsers can't even run the newest
  JavaScript syntax without help.

## Key terms

- **Module** — a single file that explicitly declares what it needs
  from other files (`import`) and what it makes available to them
  (`export`), instead of relying on load order and shared global
  variables.
- **Dependency graph** — the full set of "this module needs that
  module" relationships across a codebase, starting from one or more
  entry points.
- **Bundler** — a build tool that reads a dependency graph starting
  from an entry point and produces one (or a few) output files with
  every module included exactly once, in an order that actually
  satisfies the dependencies.
- **Transpilation** — converting source code written in a newer or
  non-standard syntax into equivalent code a target environment (an
  older browser, for instance) can actually run.

## What this unit covers

L2 works through how a bundler actually builds and resolves a
dependency graph, and what transpilation and tree-shaking add on top
of that. L3 implements a real, working dependency-graph resolver and
uses it to show exactly why manual script-tag ordering breaks the
moment a codebase's dependencies get complicated enough — and why a
bundler doesn't just reorder files, it also builds each dependency
into the output exactly once, even when several other files depend on
it.
