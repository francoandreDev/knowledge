An endpoint lists recent orders along with each customer's name. In
dev, with 20 orders, it responds in about 21 milliseconds — fast
enough that nobody thinks twice about it. In production, with 50,000
orders, the exact same endpoint takes nearly a minute. **The code
never changed between dev and production. The database schema never
changed. What actually got slower as the data grew?**

</Scenario>

## The scene in simple words

The `orders` table stores purchases: order id, customer id, date,
total, and so on. The `customers` table stores people: customer id,
name, email, address, and so on. The `customerId` on an order is the
bridge that says "this order belongs to that customer."

A **join** means asking the database to bring related rows together:
"give me the orders, and attach each matching customer." Without that
join, app code may fetch the orders first, then ask the database again
and again for each customer's name. That is not one slow question; it
is thousands of small questions.

## The shape of the problem

- A database doesn't just store data — every query against it has a
  **query plan**: a specific sequence of steps (which index to use,
  which table to scan, how to combine results) the database follows
  to answer that query. Some plans scale fine as data grows; others
  get dramatically worse.
- The classic version of this problem is the **N+1 query problem**:
  code that fetches a list of N items with one query, then issues one
  additional query _per item_ to fetch related data — 1 query becomes
  N+1 queries, and that "+1 per item" cost scales directly with the
  size of the list.
- **Normalization** (splitting related data into separate tables to
  avoid duplication) and **denormalization** (deliberately duplicating
  some data to avoid needing a join or extra lookup) are two different
  answers to the same underlying question: where should the trade-off
  between write simplicity and read speed actually sit for this
  specific access pattern?

## Key terms

- **Query plan** — the specific sequence of steps a database follows
  to execute a given query; two queries that look similar can have
  very different plans and very different performance as data grows.
  It is like choosing a route through a warehouse: walk every aisle,
  use the shelf index, combine two lists, sort boxes, then return the
  answer.
- **Join** — combining related rows from two tables, usually through a
  shared id like `customerId`, so one query can return the connected
  data together.
- **N+1 query problem** — fetching a list with one query, then issuing
  one additional query per item in that list to fetch related data,
  instead of fetching everything needed in a small, fixed number of
  queries.
- **Normalization** — structuring data so each fact is stored in
  exactly one place (e.g., a customer's name lives only in the
  `customers` table), avoiding duplication at the cost of needing
  joins or extra lookups to reassemble related data.
- **Denormalization** — deliberately duplicating some data (e.g.,
  storing a customer's name directly on each of their orders) to make
  a specific read fast, at the cost of needing to keep the duplicated
  copies in sync when the original changes.

## What this unit covers

L2 works through why query count (not just "the database is slow")
is the thing that actually explains this unit's Scenario, and what
normalization and denormalization each optimize for. L3 implements
both the naive N+1 version and a properly joined version of the
