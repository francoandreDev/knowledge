The order service calls the inventory service on every checkout, with
no timeout on that call. One day the inventory service starts
responding slowly — not down entirely, just slow. Every checkout
request to the order service now sits waiting on a slow inventory
call that never fails and never succeeds quickly. Within minutes, the
order service's own limited pool of connections fills up entirely
with stuck requests, and it stops being able to serve _any_ checkout
at all — and the same exhausted service also struggles with other
routes that are not directly about inventory. **The order
service's own code has no bug. So how did one slow dependency take
down an entirely different, otherwise-healthy service?**

## Before the technical names

A service has limited "seats" for work: worker threads, database
connections, HTTP connections, memory, and queue space. When one
request sits waiting, it keeps a seat occupied. If enough requests sit
waiting, there are no seats left for new work, even if the new work
would have been quick.

That is why a slow dependency is dangerous. The first problem is not
only "inventory is slow." The second problem is "the order service
keeps lending its limited seats to calls that may never come back."
Timeouts, retries, circuit breakers, and backpressure are ways to
protect those seats.

## The shape of the problem

- Without a **timeout**, a call to a dependency can wait indefinitely
  — a slow dependency doesn't just slow down the specific request
  that's calling it, it can tie up a resource (a thread, a
  connection) for as long as the dependency stays slow.
- A service typically has a **finite pool** of resources (worker
  threads, connections) to handle requests. If enough requests get
  stuck waiting on a slow dependency, the pool exhausts — and once
  it's exhausted, the service can't process _any_ request, even ones
  that don't touch the slow dependency at all. This is how one slow
  dependency causes a completely unrelated outage.
- Four techniques address different parts of this problem: a
  **timeout** caps how long any single call can hold a resource; a
  **retry** (with backoff) handles a transient failure without giving
  up immediately; a **circuit breaker** stops sending requests to a
  dependency that's clearly failing, instead of continuing to waste
  resources on calls likely to fail anyway; **backpressure** signals
  upstream that a system is overloaded, rather than silently queuing
  work until it collapses.
- Read the four techniques as four separate questions: "how long am I
  willing to wait?", "when is it worth trying again?", "when should I
  stop calling something broken?", and "how do I tell callers to slow
  down before I run out of seats?"

## Key terms

- **Timeout** — a maximum duration a call to a dependency is allowed
  to take before it's treated as failed, regardless of whether the
  dependency eventually would have responded.
- **Retry (with backoff)** — automatically re-attempting a failed
  call, typically waiting progressively longer between attempts, to
  handle brief, transient failures without giving up too early or
  overwhelming an already-struggling dependency.
- **Circuit breaker** — a mechanism that stops sending requests to a
  dependency after it fails repeatedly, instead of continuing to
  attempt (and wait on) calls that are very likely to fail, then
  periodically checks if the dependency has recovered.
- **Backpressure** — a signal sent upstream indicating a system can't
  keep up with the current load, so the sender can slow down or shed
  work, rather than the receiver silently queuing everything until it
  runs out of resources.

## What this unit covers

L2 works through how these four techniques fit together (they solve
different parts of the resource-exhaustion problem, not the same
part) and the states a circuit breaker actually moves through. L3
implements a timeout wrapper and a circuit breaker, verifies their
behavior directly, and applies both to the Scenario's cascading
outage.
