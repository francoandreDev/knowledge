A "remove duplicate customer IDs" function passes every test in CI, runs instantly on a
sample file, and gets merged without a second thought. Three months later, on the real
nightly import — 2,500x more rows than the test file — the job that used to take 4 seconds
now hasn't finished after 20 minutes, and someone's paged. **The code didn't change. The
machine didn't get slower. Why did the exact same function go from instant to unusable?**

The function itself never became "slower" — its **growth rate** simply means work grows
much faster than the data does, and the test file was small enough that this fact stayed
invisible.

## Quick translation before the symbols

| Word or symbol | Plain meaning in this unit                                                  |
| -------------- | --------------------------------------------------------------------------- |
| `n`            | How many records/items the function receives                                |
| Work           | How many checks, comparisons, scans, or lookups the function has to perform |
| Growth rate    | What happens to the work when `n` doubles, grows 10x, or grows 1,000x       |
| Big-O          | A shorthand for that growth shape, not a stopwatch result in milliseconds   |

The `~40,000` number in the scenario is the rough `n²` scale for 200
records. The exact count for a "scan the growing result list" version
can be closer to `0 + 1 + ... + 199 = 19,900`; both point to the same
lesson: the work grows like "the input times itself," not like "one
pass through the input."

- **Algorithmic complexity describes how the amount of work grows as the input size (`n`) grows** — not how fast the code runs on one specific input. Two functions can both "work correctly" and both "pass in 4ms locally," while having completely different growth rates that only become visible once `n` gets large enough.
- **Big-O notation names the growth rate, ignoring constant factors and lower-order details** — `O(n)` means work grows roughly proportional to `n`; `O(n²)` means work grows roughly proportional to `n` multiplied by itself. The "O" answers "as `n → ∞`, what shape does the work curve take?", not "how many milliseconds does this take on my laptop right now?"
- **This is exactly why a small test file hides the problem**: at `n = 200`, the gap between `O(n)` (200 units of work) and `O(n²)` (40,000 units of work) is invisible on modern hardware — both finish instantly. At `n = 500,000`, the same gap is 500,000 units vs. 250 billion units — one finishes in milliseconds, the other doesn't finish in a reasonable time at all.
- The practical skill this unit builds: before shipping code that processes a collection, ask **"what happens to the amount of work if `n` were 1,000x bigger?"** — not "does this pass on my test data," which is exactly the question the incident above skipped.

## The complexity classes that come up constantly

| Notation     | Name         | Work at n=10 | Work at n=1,000,000   | Typical example                            |
| ------------ | ------------ | ------------ | --------------------- | ------------------------------------------ |
| `O(1)`       | Constant     | 1            | 1                     | Reading `array[5]` by index                |
| `O(log n)`   | Logarithmic  | ~3           | ~20                   | Binary search in a sorted array            |
| `O(n)`       | Linear       | 10           | 1,000,000             | Scanning every item once                   |
| `O(n log n)` | Linearithmic | ~33          | ~20,000,000           | A good general-purpose sort                |
| `O(n²)`      | Quadratic    | 100          | 1,000,000,000,000     | Comparing every item to every other item   |
| `O(2ⁿ)`      | Exponential  | 1,024        | astronomically larger | Brute-force checking every possible subset |

The columns aren't close. At `n = 10`, `O(n)` and `O(n²)` differ by 10x — barely
noticeable. At `n = 1,000,000`, they differ by a million-fold — the entire gap between "the
page loads" and "the request times out."
