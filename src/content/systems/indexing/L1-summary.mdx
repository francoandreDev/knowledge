An app's login query — `SELECT * FROM users WHERE email = ?` —
took 2 milliseconds when the `users` table had 500 rows. Nobody
touched that query since. Two years and 2 million users later, the
exact same query takes 400 milliseconds, and login feels broken.
**The code didn't change. The query didn't change. What did, and
why does more data make an unchanged query slower — is that just an
unavoidable cost of growth, or is something fixable actually
missing?**

## The minimum database picture

Think of the `users` table as a very large spreadsheet. Each **row** is
one user. Each **column** is one kind of information about that user,
such as `email`, `name`, or `created_at`. A query like
`WHERE email = ?` means: "find the row whose email equals this value."

An index does not replace that table. It is a second, smaller lookup
structure that says "this email points to that row location." Without
the lookup structure, the database has to read row after row, the same
way you would search an unsorted notebook page by page. With the
lookup structure, it can jump near the right row first.

## The shape of the problem

- Without help, a database finds a row by a **full table scan** —
  checking every single row until it finds a match (or reaches the
  end and finds none). Scan cost grows in direct proportion to the
  number of rows: 4,000x more rows means roughly 4,000x more
  checking.
- An **index** is a separate structure, built ahead of time, that
  lets the database jump close to the answer instead of checking
  every row — the same trade every dictionary makes: the words on
  each page aren't in a special order for their content, they're
  sorted so you can find one without reading the whole book.
- The trade-off is real, not free: an index takes disk space, and
  every write to the indexed column has to update the index too — so
  indexing isn't "always turn it on everywhere," it's "turn it on for
  the columns that are actually looked up this way."

## Key terms

- **Full table scan** — checking every row in a table one by one
  until a match is found; cost grows linearly with row count.
- **Index** — a separate, ordered (or hashed) structure mapping
  column values to row locations, built specifically to make lookups
  on that column fast without scanning the whole table.
- **Row location** — the pointer an index stores so the database can
  find the real row after it finds the indexed value; the index is the
  map, not the full data.
- **B-tree** — the most common index structure: a balanced,
  sorted tree where lookup cost grows with the _logarithm_ of the row
  count, not the row count itself. Because it keeps values in sorted
  order, it also supports range queries (`WHERE age > 30`) and
  sorted output, not just exact matches.
- **Hash index** — an index built on a hash table: average-case
  constant-time exact-match lookups, but the hashing destroys value
  order, so it can't answer range or "sorted by this column"
  queries at all.
- **Selectivity** — how much an index on a column actually narrows
  the search. A column with mostly-unique values (like `email`) is
  highly selective and indexes well; a column with only a few
  distinct values (like `is_active: true/false` on its own) narrows
  almost nothing and often isn't worth indexing by itself.

## What this unit covers

L2 works through why full-scan cost grows linearly while a B-tree's
grows logarithmically — and what that difference actually means at
2 million rows — plus when a hash index is the better (or the only
usable) choice, and cases where an index quietly doesn't get used at
all. L3 builds a real in-memory full scan, sorted-array binary
search (a B-tree's lookup behavior without the on-disk tree
machinery), and a hash index in code, benchmarks all three against
the opening scenario's exact 500-vs-2,000,000-row jump, and shows
concretely why the hash index can't answer a range query that the
sorted structure answers for free.
