Open two tabs running the same little script. In tab A, run
`counter = 999`. Switch to tab B, run `console.log(counter)`. It prints
`0` — as if tab A's assignment never happened. Nobody would call this a
bug: everyone already knows, intuitively, that two browser tabs "don't
talk to each other." But _why not_, mechanically? They're running the
exact same code, on the exact same machine, at the exact same time.

**The answer is the same reason a crashed Node process, a Python script
you `Ctrl+C`, and a server that "runs out of memory" are all explained by
one OS concept: the process.**

</Scenario>

- A program on disk is just bytes in a file — nothing happens until the OS turns it into a **process**: a running instance with its own memory, its own view of the machine, and OS-tracked state. That's why tab A's `counter` and tab B's `counter` are different variables in different memory even though the source code is identical — each tab runs as its own process (or process-like isolate), and a process's memory belongs to nobody else.
- A process never touches hardware directly. Every interaction with the outside world — reading a file, allocating memory, sending a packet — goes through the OS via a **system call**, crossing from **user mode** to **kernel mode** and back.
- Each process gets its own **virtual address space**, laid out in regions:
  - **text** — the program's compiled code (read-only)
  - **data/bss** — global and static variables
  - **heap** — dynamic allocations (`malloc`, `new`, objects), grows upward
  - **stack** — function call frames and local variables, grows downward
- **Virtual memory** means every process believes it owns the _entire_ address space. The CPU's MMU and the OS's page tables translate virtual addresses to real physical RAM — this translation layer is exactly what makes process isolation possible: one process's pointers simply have no valid mapping into another's memory.
- What looks like many processes running "at once" on a machine with fewer CPU cores than processes is the OS **scheduler** rapidly **context-switching** between them, giving each a slice of CPU time.
- A **segmentation fault** is the OS refusing an access to a virtual address that has no valid mapping — not a hardware failure, a permissions decision.

| Term                  | One-line meaning                                            |
| --------------------- | ----------------------------------------------------------- |
| Process               | A running instance of a program, with its own memory & PID  |
| PID                   | The OS's unique numeric name for a running process          |
| Virtual address space | Every address a process can use — private, not shared       |
| Page table            | Per-process map from virtual addresses to physical RAM      |
| System call           | The only door from user code to kernel-controlled resources |
| Context switch        | The scheduler swapping which process the CPU is running     |
| Segfault              | An access to a virtual address with no valid mapping        |

Key terms: process, PID, virtual address space, page table, MMU, text/data/heap/stack segments, system call, context switch, kernel mode/user mode, segfault.
