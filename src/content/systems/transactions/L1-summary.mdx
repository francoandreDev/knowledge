Placing an order does two things: decrement the product's stock count,
then insert a new order record. A customer places an order, the stock
count visibly drops — and then the order never shows up in their order
history. Support pulls the logs: the stock decrement succeeded, but
the order insert failed a moment later and nobody rolled the decrement
back. **Two writes, one request, and only one of them actually
happened. If the code ran exactly as written, what's actually missing
— a bug in either step, or something neither step was ever responsible
for?**

</Scenario>

## Plain-word translation first

In this unit, a **table** is just a structured list, like a spreadsheet
inside the database. A **record** is one row in that list. A **write**
means the app changed or added a row. A **request** is the user's
action asking the app to do work, such as "place this order." A
**rollback** means "undo the changes we already made because the whole
action did not finish safely."

So the story has two lists: one list says how much stock is left, and
another list stores placed orders. The confusing failure is that the
app may have told the user the request was handled, or may have visibly
changed stock, while the database never reached the only moment that
matters: **commit**, the point where the whole action becomes real as
one completed unit.

## The shape of the problem

- Most real actions aren't a single write — placing an order touches
  stock _and_ the order table; transferring money touches one balance
  _and_ another. If either write can fail independently of the other,
  "partially done" is a real, reachable state, not a hypothetical one.
- Neither individual write did anything wrong: the stock decrement
  really did need to happen, and the order insert really did fail for
  its own separate reason. The bug isn't in either step — it's that
  nothing treated the two steps as one indivisible unit.
- A **transaction** is exactly that: a way of saying "these operations
  either all happen, or none of them do" — turning "partially done" from
  a possible outcome into one the system refuses to leave you in.

## Key terms

- **Transaction** — a group of operations treated as a single unit:
  they all succeed together, or the system undoes anything that
  already happened and leaves the data as if none of them ran.
- **ACID** — the four properties a real transaction system guarantees:
  **A**tomicity (all-or-nothing), **C**onsistency (data-level rules,
  like "stock can't go negative," always hold), **I**solation
  (concurrent transactions don't see each other's half-finished work),
  **D**urability (once a transaction reports success, that result
  survives a crash immediately afterward).
- **ACID in one breath** — Atomicity asks "did the whole action finish,
  or do we undo it?"; Consistency asks "did the data rules stay true?";
  Isolation asks "can another request see my half-finished work?";
  Durability asks "after success, can a crash erase what we promised?"
- **Rollback** — undoing every change made so far in a transaction,
  restoring the exact state from before it started.
- **Commit** — making a transaction's changes permanent and visible,
  only once every operation in it has succeeded.
- **Write-ahead log** — a durability mechanism: changes are written to
  a persistent, append-only log _before_ the system reports success,
  so a crash immediately after can still recover the change from the
  log.

## What this unit covers

L2 works through what each of the four ACID properties actually
guarantees, using the stock/order scenario above as the running
example, plus what a transaction's lifecycle looks like from begin to
commit-or-rollback. L3 implements a real, working transaction wrapper
in code — reproducing the exact stock/order bug from a naive
implementation, then fixing it with a version that rolls back cleanly
on failure, and a small write-ahead-log simulation demonstrating
durability across a simulated crash.
