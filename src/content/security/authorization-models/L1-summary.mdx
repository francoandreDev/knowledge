A hotel guest holds a genuine key card for room 214. Out of curiosity they tap it
on room 215, next door, and the door unlocks. The card is real, issued by the
hotel, and not expired. **The lock accepted a valid card. So why did it open a room that
card was never meant for?**

The lock only asked "is this a card the hotel issued?" It never asked "is this
card allowed to open this particular door?" The first question is about who
you are. The second is about what you may do, and the lock skipped it.

## The same bug, in software

Replace the hotel with a web service. An engineer tests their own account and
sees their invoice at `GET /api/invoices/48213`. They change the number to
`48212`, and the server returns `200 OK` with a stranger's name, address and
billing history. The endpoint required a login, and the request came from a
genuinely logged-in user. It checked identity and never checked access.

| Question                                                           | Name                            | Hotel version                      | Bug if skipped                                         |
| ------------------------------------------------------------------ | ------------------------------- | ---------------------------------- | ------------------------------------------------------ |
| Is there a valid, logged-in session?                               | Authentication                  | Is this a real hotel card?         | Anyone can use the system                              |
| Is this kind of user allowed this kind of action?                  | Authorization (role check)      | Do guests get to open guest rooms? | A role does things it should never do                  |
| Does this specific thing belong to / relate to this specific user? | Authorization (attribute check) | Is the card for room 215?          | Any valid user reaches every resource: the invoice bug |

The invoice endpoint passed the first row and skipped the third.

## The bug has a name

- **Authentication and authorization answer different questions, and a system can
  get the first completely right while failing the second.** "This request comes from
  a real, logged-in user" says nothing about "this user may open this resource."
- **Checking login but not ownership is called Insecure Direct Object Reference
  (IDOR).** It is one of the most commonly reported web vulnerabilities because an
  endpoint that "obviously" requires login is easy to write without noticing the
  missing second check.
- **The user cannot be trusted to supply only their own IDs.** Anything in a URL or
  request body can be edited by the person sending it, so the server has to
  compare the requested resource against the requester every time.

## Two models for deciding

An **authorization model** is the systematic answer to "what decides whether this
request succeeds." Two common ones:

| Model | Permissions are attached to...                       | Example rule                           | Answers                                     |
| ----- | ---------------------------------------------------- | -------------------------------------- | ------------------------------------------- |
| RBAC  | A role (a named bucket of permissions)               | `billing-viewer` can view invoices     | Can this KIND of user do this KIND of thing |
| ABAC  | Attributes of the user, the resource and the context | `user.id` must equal `invoice.ownerId` | Can THIS user do this to THIS resource      |

RBAC alone cannot express the invoice fix. "A billing-viewer may view invoices" is
true for every billing-viewer and every invoice. Only a comparison between the
requester's attributes and the resource's attributes can say "this one, yes; that one,
no." The practical question for any endpoint is **"is this specific actor allowed to
act on this specific resource?"**
