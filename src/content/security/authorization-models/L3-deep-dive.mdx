## The vulnerable handler, reproducing the exact incident

Read the code with this small legend:

| Code piece | Human idea                                       |
| ---------- | ------------------------------------------------ | --- | -------------------------------- |
| `users`    | The known users and their roles                  |
| `invoices` | The known invoices and who owns each one         |
| `throw`    | Stop and return an error instead of private data |
| `return`   | Send the answer back                             |
| `===`      | Compare whether two values are exactly equal     |
| `          |                                                  | `   | "or": either condition is enough |

For the errors: no login gives `401`; invoice missing gives `404`; invoice exists but is
not yours gives `403`.

```js
// invoices.js — a simplified store and the ORIGINAL, vulnerable handler
const invoices = {
  48212: { id: 48212, ownerId: 7, amount: 120 },
  48213: { id: 48213, ownerId: 42, amount: 340 },
};
const users = {
  42: { id: 42, role: "billing-viewer" },
  7: { id: 7, role: "billing-viewer" },
  1: { id: 1, role: "billing-admin" },
};

function getInvoiceVulnerable(currentUserId, invoiceId) {
  const user = users[currentUserId];
  if (!user) throw new Error("401 Unauthorized");

  const invoice = invoices[invoiceId];
  if (!invoice) throw new Error("404 Not Found");

  return invoice; // BUG: authenticated, but never checked ownership
}
```

```js
// Reproducing L1's incident exactly: user 42 requests invoice 48212, owned by user 7
getInvoiceVulnerable(42, 48212);
// { id: 48212, ownerId: 7, amount: 120 } — returned successfully, no error at all
```

The function correctly checks that `currentUserId` maps to a real, authenticated user —
that check works exactly as intended. **It never once compares `invoice.ownerId` against
`user.id`** — the ABAC-style attribute comparison from L2 simply doesn't exist in this
code, which is precisely why any authenticated user can fetch any invoice by ID.

## The fixed handler — one added comparison

```js
function getInvoiceFixed(currentUserId, invoiceId) {
  const user = users[currentUserId];
  if (!user) throw new Error("401 Unauthorized");

  const invoice = invoices[invoiceId];
  if (!invoice) throw new Error("404 Not Found");

  const isOwner = invoice.ownerId === user.id;
  const isAdmin = user.role === "billing-admin";
  if (!isOwner && !isAdmin) throw new Error("403 Forbidden");

  return invoice;
}
```

```js
try {
  getInvoiceFixed(42, 48212); // user 42 requesting user 7's invoice
} catch (e) {
  console.log(e.message); // "403 Forbidden"
}

getInvoiceFixed(7, 48212); // the actual owner — succeeds
getInvoiceFixed(1, 48212); // billing-admin — succeeds via the role clause
```

**Neither the `users` object nor the `invoices` object changed at all.** The fix is
entirely the added `isOwner`/`isAdmin` check — exactly the missing row from L1's table,
implemented as two boolean comparisons and a guard clause, meaning an early check that
stops the function before private data can be returned.

<Checkpoint question="getInvoiceFixed(1, 48212) succeeds because user 1 is a billing-admin, not because they own invoice 48212. Trace through the function: which specific line lets that request through, and why doesn't it need isOwner to be true?">

The line is `if (!isOwner && !isAdmin) throw new Error("403 Forbidden")`.
For user 1, `isOwner` evaluates to `false` (`invoice.ownerId` is `7`, not
`1`), but `isAdmin` evaluates to `true` (`user.role === "billing-admin"`).
Because the guard only throws when _both_ are false, a true `isAdmin`
alone is enough to satisfy the condition and let execution continue past
the guard to `return invoice`. This is exactly the OR-shaped rule from
L2's ABAC example (`user.id == invoice.ownerId OR user.role ==
"billing-admin"`) expressed as code: ownership and admin-role are two
independent, either-is-sufficient paths to the same allow decision, not
two things that both have to be true.

</Checkpoint>

## The RBAC and ABAC checks, as separate, composable functions

```js
// A real system typically separates these two kinds of checks
function rbacAllows(role, permission) {
  const ROLE_PERMISSIONS = {
    "billing-viewer": ["view-invoice", "view-billing-history"],
    "billing-admin": [
      "view-invoice",
      "view-billing-history",
      "edit-invoice",
      "refund-invoice",
    ],
  };
  return (ROLE_PERMISSIONS[role] || []).includes(permission);
}

function abacAllowsViewInvoice(user, invoice) {
  return invoice.ownerId === user.id || user.role === "billing-admin";
}
```

```js
rbacAllows("billing-viewer", "view-invoice"); // true — role has this permission
rbacAllows("billing-viewer", "refund-invoice"); // false — role lacks this permission

abacAllowsViewInvoice({ id: 42, role: "billing-viewer" }, { ownerId: 7 }); // false
abacAllowsViewInvoice({ id: 7, role: "billing-viewer" }, { ownerId: 7 }); // true
```

A real endpoint combines both: `rbacAllows` gates whether the _kind_ of action is even
possible for this role, and `abacAllowsViewInvoice` gates whether _this specific_ resource
is accessible to _this specific_ user. Neither function alone reproduces the fixed
handler's behavior — `rbacAllows("billing-viewer", "view-invoice")` returns `true`
regardless of which invoice ID is requested, and would incorrectly allow the original bug
if used alone.

## Extend the incident: what if the resource has a more complex ownership rule?

L1 and L2's ownership check was a simple one-to-one comparison (`invoice.ownerId ===
user.id`). First learn that one-to-one case. Team ownership is the same idea with a list
instead of one ID: "is this user in the group that owns this resource?" **What changes if
invoices can belong to a whole team, not just one user — does the same ABAC pattern still
work?**

```js
function abacAllowsViewTeamInvoice(user, invoice, userTeamIds) {
  const isTeamMember = userTeamIds.includes(invoice.teamId);
  return isTeamMember || user.role === "billing-admin";
}

abacAllowsViewTeamInvoice(
  { id: 42, role: "billing-viewer" },
  { teamId: "team-9" },
  ["team-9", "team-12"], // user 42's team memberships
); // true — user is on team-9
```

The pattern generalizes directly: the comparison shifts from a single ID match to a
membership check against a list, but it's still an attribute-of-the-user-vs-attribute-of-
the-resource comparison — the same ABAC shape as before, just with a richer relationship
than strict ownership. **This is the actual generalizable lesson**: whatever the specific
relationship is (owns, is-on-the-same-team-as, is-assigned-to), an authorization check has
to encode it explicitly — authentication alone, and even a correct role check alone, never
implies it.

<Checkpoint question="A new feature lets invoices be shared with a specific list of individual coworkers, not just a team. Does abacAllowsViewTeamInvoice's shape (an attribute-of-user vs. attribute-of-resource comparison) still apply, or does sharing need a fundamentally different kind of check?">

The same shape still applies. Ownership was a single-ID equality check
(`invoice.ownerId === user.id`), team access widened that to a
membership check against a list (`userTeamIds.includes(invoice.teamId)`),
and per-user sharing is the same membership check with a different list —
something like `invoice.sharedWithUserIds.includes(user.id)`. In every
case the function is still comparing an attribute pulled from the
requesting user against an attribute pulled from the resource; only the
specific relationship being tested changes (owns, is-on-a-team-with,
is-shared-with). What would actually require a different kind of check is
a rule that can't be reduced to comparing the two sides at all — for
example, "only during business hours" pulls in a fact about the current
context instead of either the user or the resource, which is why ABAC
treats context as a third, separate input alongside user and resource
attributes.

</Checkpoint>

## Failure modes

| Failure mode                                                                    | What it gets wrong                                                                                                                                                       |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Assuming a valid login implies authorization to access any specific resource    | Authentication and authorization are separate checks — the invoice bug passed authentication perfectly and still leaked private data                                     |
| Using only RBAC for resource-specific access control                            | `rbacAllows("billing-viewer", "view-invoice")` is true regardless of which invoice — role checks can't express per-resource ownership by design                          |
| Adding the ownership check only to some endpoints that return user data         | Any endpoint accepting a resource ID from the request is a candidate for this exact bug class — the audit needs to cover all of them, not just the one that was reported |
| Treating a "found the bug in one place, fixed it" as the whole task             | The generalizable fix is the AUDIT QUESTION (is there an attribute comparison for every ID-accepting endpoint), not just the one line changed in the reported endpoint   |
| Assuming complex ownership (teams, shared resources) can't use the same pattern | The comparison shape stays the same (attribute of user vs. attribute of resource) even when the relationship is richer than a single ID match                            |
