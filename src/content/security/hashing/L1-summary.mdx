A download page publishes a file's hash next to the download link. After
downloading, hashing the file yourself and comparing it to the published
value tells you, with near-certainty, whether the file arrived intact —
without ever needing to compare the file byte-by-byte against a trusted
copy. **How can a single short string stand in for an entire file's
integrity, and why does changing one character of the file scramble that
string completely instead of changing it just a little?**

## Before the crypto words

| Term          | Plain meaning                                                      |
| ------------- | ------------------------------------------------------------------ |
| **Bit**       | One tiny yes/no value: `0` or `1`                                  |
| **Byte**      | 8 bits grouped together; files are made of many bytes              |
| **Hash**      | A fixed-size fingerprint for some input                            |
| **Integrity** | The file was not changed from the trusted version                  |
| **One-way**   | Practical to compute forward, not practical to reverse             |
| **KDF**       | A deliberately slow password hash, used to make guessing expensive |

Fast can be good or bad depending on the job. If you are checking a
thousand downloaded files, you want the hash to be fast. If an attacker
is trying a billion password guesses against a stolen database, you want
each guess to be slow.

## The shape of the problem

- A cryptographic hash function takes input of any size and produces a
  fixed-length, deterministic fingerprint — the same input always
  produces the same output, but there's no practical way to work
  backwards from the fingerprint to the input.
- A hash function being "one-way" and "fast" are two independent
  properties — most hash functions are both, which is exactly right for
  checking file integrity and exactly wrong for storing passwords, a
  distinction this unit exists to make precise.

## Key terms

- **Deterministic** — the same input always produces the exact same
  hash, every time, on any machine.
- **Avalanche effect** — changing even a single bit of the input should
  scramble the output completely and unpredictably, not shift it
  slightly — this is what makes a hash useful as a tamper-detector.
- **Collision resistance** — it should be computationally infeasible to
  find two different inputs that produce the same hash.
- **Preimage resistance** — given only a hash, it should be infeasible
  to find any input that produces that hash.
- **Key derivation function (KDF)** — a hash function deliberately built
  to be _slow_ and _tunable_, specifically for turning a password into a
  stored credential; this is the missing half of the picture from
  `security/authentication-fundamentals`, which used a KDF (`scrypt`)
  without explaining what structurally separates it from an everyday
  hash like SHA-256.

If you arrived here from passwords, `/security/authentication-fundamentals/`
explains the login flow, salting, and rainbow-table problem this unit
builds on.

## What this unit covers

L2 works through the formal properties every cryptographic hash needs
(deterministic, fixed-length, avalanche effect, collision resistance),
and what specifically changes in a KDF's design to make it deliberately
expensive. L3 demonstrates the avalanche effect and a real collision
search with runnable code, and works through tuning a KDF's cost
parameter to see the actual trade-off between login latency and
attacker cost.
