A shop spent a lot on its front-door lock. A stranger never touched it. They
walked in through an old service entrance that nobody remembered, then asked
the clerk for receipt number 1042. The clerk handed it over, and then
handed over 1043 and 1044 too, because the clerk only checked that the
stranger was _inside the shop_, never whose receipt it was. **If the lock
was never the weak point, what was?**

The weak points were boring: a forgotten door and a clerk who never asked
"is this yours?" A web app has the same shape. Its strongest defenses
(password storage, HTTPS, session tokens) can be excellent while an old route
or a missing ownership check lets someone walk straight past them.

## Why do attackers ignore your best lock?

An attacker is paid in results, not in style. They list every place the app
accepts input (its **attack surface**), try cheap guesses in each, and move
on from anything that resists. Strong cryptography is expensive to attack, so
it is rarely where they start.

| Attacker question                     | Cheap if...                                 | Category it points at          |
| ------------------------------------- | ------------------------------------------- | ------------------------------ |
| Can I change the number in this URL?  | the server never checks who owns the record | Broken access control          |
| Can I type something strange here?    | the app pastes input into a command         | Injection                      |
| Is there an old route still online?   | nobody removed it after a release           | Security misconfiguration      |
| Does this library have a public flaw? | the app never updated it                    | Vulnerable and outdated pieces |
| Can I make the server fetch a URL?    | the server fetches whatever it is told      | Server-side request forgery    |

## What are the ten categories, and how do they group?

The **OWASP Top 10** is not one vulnerability. It is a periodically re-ranked
list of the categories of mistake that keep showing up in real incidents. Ten
names are hard to hold, so group them by the question each one answers.

| Family                       | Question it answers                              | Categories                                                        |
| ---------------------------- | ------------------------------------------------ | ----------------------------------------------------------------- |
| Who may do what              | Is this person allowed to do this?               | Broken access control; identification and authentication failures |
| Input that becomes a command | Did the app treat input as data?                 | Injection; server-side request forgery (SSRF)                     |
| Protecting data              | Is sensitive data safe where it sits or travels? | Cryptographic failures; software and data integrity failures      |
| Setup and upkeep             | Is the system configured and maintained safely?  | Security misconfiguration; vulnerable and outdated components     |
| Design and visibility        | Did we plan for abuse, and can we see it?        | Insecure design; security logging and monitoring failures         |

Two categories per family, five families, ten categories. The grouping is a
memory aid for this unit, not an official OWASP structure.

## Key terms

- **Attack surface** — every place an attacker can send input to the system or
  read output from it: endpoints, form fields, headers, dependencies.
- **Injection** — untrusted input is run as a command by something downstream
  (a database, a shell) instead of being treated as plain data.
- **Broken access control** — the system confirms _who_ you are but does not
  enforce _what you may touch_.
- **Security misconfiguration** — the code is fine, the setup is not: a debug
  page left on, a default password never changed.
- **Endpoint** — one specific URL the app answers, like `/api/invoices/42`.
