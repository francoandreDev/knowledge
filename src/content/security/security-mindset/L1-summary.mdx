Two teams ship the exact same feature the same week: a "resend password
reset email" button. Team A writes it, tests that clicking the button sends
an email, and ships. Team B writes the identical feature, but first spends
twenty minutes asking "if I wanted to abuse this, what would I do?" — and
catches that nothing stops the endpoint from being called thousands of
times in a row for the same address.

| Team | Pre-launch step              | What happened 6 months later                                                   |
| ---- | ---------------------------- | ------------------------------------------------------------------------------ |
| A    | Functional test only         | A script called the endpoint on repeat, email-bombing 40,000 inboxes overnight |
| B    | 20-minute adversarial review | Nothing — a rate limit added at design time closed the gap for free            |

**Both teams shipped code that "worked" — clicking the button, once, did exactly what it was supposed to. Why did only one of them get paged at 3 a.m.?**

</Scenario>

Team A's code passed every test anyone wrote. Nobody wrote a test for "what
if someone calls this ten thousand times" — because that's not a question
functional testing asks in the first place.

Before the security labels, translate the scenario's technical words:

| Term           | Plain meaning                                                                |
| -------------- | ---------------------------------------------------------------------------- |
| `endpoint`     | A URL/action the server responds to, like "send another reset email"         |
| `script`       | A small program that can repeat an action much faster than a person clicking |
| `rate limit`   | A rule like "only 3 tries per minute"                                        |
| `happy path`   | The normal expected use: one real user clicks once                           |
| `email-bombed` | Many unwanted emails sent to the same inboxes until they become unusable     |

The first security move is still simple: ask what happens if someone
uses the feature in a way the product never intended. STRIDE only gives
names to those simple "how could this be abused?" questions.

- Correctness testing asks "does this do what it's supposed to do for the inputs I expect?" Security asks a fundamentally different question: "what can this do if someone deliberately sends inputs I _didn't_ expect, with intent to misuse it?"
- The **security mindset** is thinking like an adversary, not a user — actively asking "how would I break this" instead of just "does this work" — and it doesn't come naturally, because normal engineering practice optimizes for the happy path.
- **Threat modeling** is the structured version of that question: for a given system, who might attack it, what would they want, and what's the easiest path to get it? It's done _before_ something breaks, not after — the twenty minutes Team B spent is the entire practice, at its smallest scale.
- A simple, durable framework: **STRIDE** — Spoofing (pretending to be someone else), Tampering (altering data/code), Repudiation (denying an action happened), Information disclosure (leaking data), Denial of service (making it unavailable), Elevation of privilege (gaining access you shouldn't have). Each is a different _category_ of "what could go wrong," not a specific bug.

- **Trust boundaries** matter more than any single line of code: the moment data crosses from something you don't control (user input, a third-party API, a file upload) into something you do, every assumption about that data has to be re-earned, not inherited.
  A non-technical version: "amount I typed into a form" is not as
  trustworthy as "amount calculated by the bank's own system." The first
  crossed a boundary from outside; the second was produced inside.
- Security is not a feature you add at the end — a system "working" only tells you the intended paths function; it says nothing about the paths nobody intended, which is exactly where attackers operate. Team A's endpoint "worked" right up until the paths nobody intended got used.
- "We're too small to be targeted" doesn't hold up either — most real-world exploitation of small or obscure systems is automated and untargeted (a script trying a known pattern across millions of hosts), not a person who specifically chose your company.
- The goal of this unit isn't to memorize specific vulnerabilities (that's `/security/owasp-top-10/` and later units) — it's building the reflex to ask "what's the worst thing an adversary could do here" as a normal part of reviewing any design, not a separate pass done by someone else, the same twenty minutes that separated Team A from Team B.
