Two companies get breached on the same day. Both lose a full copy of their
user database — 2,000,000 accounts each. Company A stored passwords as
plain text. Company B stored a salted hash of each password, never the
password itself.

| Company | How passwords were stored | What the attacker actually got                           |
| ------- | ------------------------- | -------------------------------------------------------- |
| A       | Plain text                | Every real password, for all 2M accounts, immediately    |
| B       | Salted hash               | 2M unreadable fingerprints — no password directly usable |

**Both companies lost the exact same database. Why does only Company A owe every one of its 2 million users a forced password reset, while Company B can honestly tell its users nothing needs to change?**

</Scenario>

The difference isn't luck — it's a design decision made long before the
breach, about what gets stored and how it can (or can't) be turned back
into a real password.

- **Authentication** answers "who are you" — a distinct question from **authorization** ("what are you allowed to do"), covered in a later unit. Confusing the two is a common source of real bugs (an endpoint that checks _whether_ you're logged in, but never checks _what_ the logged-in user is allowed to access).
- Proof of identity comes from one or more of three categories, traditionally:

Multi-factor authentication means combining categories, not just requiring two things from the _same_ category — two passwords is still one factor.

- **A password should never be stored as plain text — and, less obviously, it shouldn't be stored merely encrypted either.** Encryption is reversible by design (that's the point, for data you need back) — a password only ever needs to be _checked_, never retrieved, so the right primitive is a one-way hash, not a two-way encryption scheme. This is exactly the decision that separated Company A from Company B above.
- **Hashing** turns a password into a fixed-length, effectively irreversible fingerprint — checking a login means hashing the entered password and comparing hashes, never comparing (or even having access to) the original. This is covered in depth in `security/hashing`; this unit only needs the "why a hash, not encryption" distinction.
- **Salting** adds a unique, random value to each password before hashing, stored alongside the hash — its purpose is specifically to defeat precomputed lookup tables (rainbow tables): without a salt, two users with the identical password produce the identical hash, which a precomputed table can crack instantly for both at once; with a per-user salt, each hash is unique even for identical passwords.
- **Sessions and tokens** are how a system avoids re-checking a password on every single request after the initial login — a session ID or token stands in for "this request came from someone who already proved their identity," and protecting _that_ value becomes its own security problem, distinct from protecting the original password.
- The practical mental model this unit builds: authentication is a chain (prove identity once → get a credential that stands in for that proof → present the credential on subsequent requests), and a real vulnerability can live in any link of that chain, not just in "how the password is stored."
