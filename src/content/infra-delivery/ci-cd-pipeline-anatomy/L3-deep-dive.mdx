## Where does the line live?

Read the fragment as a recipe: `steps` run in order, `run` is the command
of each step, and `continue-on-error` means "even if this command fails,
keep going". Hostnames and script names here are made up.

```yaml
- name: Test
  run: npm test
  continue-on-error: true # left over from a flaky-test workaround, 2 weeks ago
- name: Deploy to production
  run: ./deploy.sh production
```

With that flag, a failing test suite still reports the step as passed at
the job level, and nothing stops the next step. The fix is deleting one
line, and the gate is real again. The rule behind it is small enough to
write as a table, which covers every case the incident touched:

| Step result | Step is bypassable | Pipeline does       |
| ----------- | ------------------ | ------------------- |
| pass        | either             | Continue            |
| fail        | no                 | Halt at this step   |
| fail        | yes                | Record it, continue |

The pipeline never "decides" anything clever: it halts at the first step
that fails and is not bypassable. The incident used the third row on the
one step that should only ever use the second.

<Checkpoint question="If you add a staging deploy step with no bypass flag between the test step and the production deploy, does that change the outcome of the incident?">

Only if staging itself fails. The failing test is still recorded and
tolerated, so the pipeline moves on to staging. If staging passes, the
production deploy runs exactly as before. If staging fails, the pipeline
halts there, which is row 6 of L2's table. A later blocking gate can
rescue a bypassed one, but only by luck: it catches different problems.

</Checkpoint>

## Why is a config change a big change?

**The flag sat in the config for two weeks. What practice would have
caught it?** Pipeline configuration is code, and it is easy to treat it as
low-stakes because it ships no user-facing feature. But a change to a
deploy gate decides what every future commit is allowed to ship, so its
blast radius is often larger than most application changes. A reviewer
asking "why is this override here and when does it come out?" turns a
silent leftover into an open question.

| Failure mode                                                  | What it gets wrong                                                   |
| ------------------------------------------------------------- | -------------------------------------------------------------------- |
| Bypass applied to the correctness gate (tests)                | The one stage built to catch bugs becomes a no-op                    |
| Temporary override with no ticket or removal plan             | It outlives its justification and becomes a permanent, invisible gap |
| Artifact rebuilt separately per environment                   | Staging and production may no longer run the same thing              |
| Rollback designed only after a bad deploy is live             | Slower and riskier than a rehearsed path                             |
| Pipeline config treated as lower-stakes than application code | A gate change can have a larger blast radius than feature code       |

## Extend the case

This unit followed one pipeline, one flag, one outage. It is a case, not
the whole territory. Try changing the story and predicting what the table
and the checklist do:

- What if the bypass had been on the staging step instead of the tests?
  Which bug class loses its safety net?
- What if the pipeline ran tests twice, once before and once after
  staging? Does a bypass on one of them still reach production?
- What if the broken commit had been caught only after reaching 60
  minutes of traffic? Use the rollback demo to compare with a 5 minute
  rehearsed path.
- What would a review checklist for pipeline changes need to ask, beyond
  "does the pipeline still run"?
