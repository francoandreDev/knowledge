## The actual pipeline config, reproducing the incident

Read the YAML below as a recipe, not as magic syntax: `on: [push]`
means "run when someone uploads a change," `steps` are the ordered
actions, `run` is the command for a step, and `continue-on-error` means
"even if this command fails, keep going." That last line is the one that
turns a real test gate into a warning nobody has to obey.

```yaml
# .github/workflows/deploy.yml — the ACTUAL config that shipped the bug
name: Deploy
on: [push]
jobs:
  pipeline:
    runs-on: ubuntu-latest
    steps:
      - name: Build
        run: npm run build

      - name: Test
        run: npm test
        continue-on-error: true # left over from a flaky-test workaround, 2 weeks ago

      - name: Deploy to production
        run: ./deploy.sh production
```

With `continue-on-error: true` on the Test step, a failing test suite
still reports the step as passed at the job level — nothing stops the
`Deploy to production` step from running immediately after, regardless of
what `npm test` actually reported.

```yaml
# THE FIX — a single line removed
- name: Test
  run: npm test
  # continue-on-error line deleted entirely — the test gate is real again
```

## Modeling the exact same logic in runnable code

The next snippet is not a real CI/CD service; it is a small model of
the rule we care about: when a step fails, does the pipeline stop, or
does a flag tell it to continue?

```js
// A minimal model of the gating logic above, general enough to test directly
function runPipeline(steps) {
  const results = [];
  for (const step of steps) {
    const passed = step.run();
    results.push({ name: step.name, passed });
    if (!passed && !step.continueOnError) {
      return { results, deployed: false, stoppedAt: step.name };
    }
  }
  return { results, deployed: true, stoppedAt: null };
}
```

```js
// Reproducing the incident exactly: continueOnError left true on a FAILING test
const buggyPipeline = [
  { name: "build", continueOnError: false, run: () => true },
  { name: "test", continueOnError: true, run: () => false }, // failing, but tolerated
  { name: "deploy-production", continueOnError: false, run: () => true },
];
runPipeline(buggyPipeline);
// { results: [...], deployed: true, stoppedAt: null }
// The failing test didn't stop anything — exactly the incident.
```

```js
// The fix: continueOnError removed from the test step
const fixedPipeline = [
  { name: "build", continueOnError: false, run: () => true },
  { name: "test", continueOnError: false, run: () => false }, // same failure, now real
  { name: "deploy-production", continueOnError: false, run: () => true },
];
runPipeline(fixedPipeline);
// { results: [...], deployed: false, stoppedAt: "test" }
// The pipeline correctly halts before reaching deploy.
```

Nothing about `runPipeline` itself changed between the buggy and fixed
runs — the exact same function, given the exact same kind of failure,
produces completely different outcomes purely based on one boolean flag
on one step. This mirrors the real incident precisely: the bug was never
in the pipeline's core logic, it was in one leftover configuration value.

<Checkpoint question="If you added a fourth step to buggyPipeline — a 'deploy-staging' step with continueOnError: false, placed between test and deploy-production — would that change the outcome of the incident scenario above?">

No. `runPipeline` stops at the _first_ step that both fails and has
`continueOnError: false`. In the incident, the `test` step fails but has
`continueOnError: true`, so the loop never treats it as a stopping
condition — it just records the failure and moves on. Whether a
`deploy-staging` step exists afterward doesn't matter, because the loop
never reaches the point of evaluating it as a halt condition; it would
run (and presumably "pass," since nothing about it is broken) exactly
like `deploy-production` did. The bug isn't about how many steps come
after the flaky flag — it's that the one step actually capable of
catching the real problem was told to never stop anything, no matter
what came next.

</Checkpoint>

## Artifact promotion, modeled the same way

```js
// The SAME artifact moves through each environment — never rebuilt per stage
function promoteThroughEnvironments(artifactId, environments) {
  const promoted = [];
  for (const env of environments) {
    if (!env.gate(artifactId)) {
      return { promoted, blockedAt: env.name };
    }
    promoted.push(env.name);
  }
  return { promoted, blockedAt: null };
}
```

```js
const environments = [
  { name: "staging", gate: (id) => runSmokeTests(id) },
  { name: "production", gate: (id) => hasManualApproval(id) },
];
promoteThroughEnvironments("build-8231", environments);
```

The same `artifactId` is checked against each environment's own gate in
sequence — `build-8231` that passes staging's smoke tests is the _exact
same build_ that later needs production's approval gate, never a
freshly-rebuilt copy that could have drifted from what staging actually
verified.

<Checkpoint question="Suppose promoteThroughEnvironments were rewritten so each environment called its own 'npm run build' right before checking its gate, instead of reusing one artifactId passed in from outside. Would the function's return value still tell you anything meaningful about whether staging and production ran the same code?">

Not reliably. The whole guarantee of `promoteThroughEnvironments` comes
from passing a single, already-built `artifactId` through every
environment's gate unchanged — the function's return value (`promoted`,
`blockedAt`) is only meaningful as a claim about _that one artifact_
passing or failing each gate. If each environment rebuilt from source
instead, `env.gate(artifactId)` would be checking a fresh build that
merely shares a source commit with the others, not the literal thing
that passed the previous gate. The function would still run and return
something, but "staging passed" would no longer imply "the thing
approved for staging is the thing reaching production" — which is
exactly the guarantee artifact promotion exists to provide.

</Checkpoint>

## Extend the incident: what if the bypassed gate had been caught in review?

**The `continue-on-error: true` line sat in the pipeline config for two
weeks. Could a different practice have caught it before the second
incident?** Pipeline configuration is code, and it's easy to treat it as
lower-stakes than application code because it doesn't ship a user-facing
feature — but a change to a deploy gate has arguably higher blast radius
than most application code changes. Treating pipeline config changes with
the same review rigor as application code (a visible diff, a reviewer who
asks "why is this override here and when does it come out") would have
surfaced the leftover flag as an open question well before the second
incident forced the issue.

## Failure modes

| Failure mode                                                                                                | What it gets wrong                                                                                                               |
| ----------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Applying `continue-on-error` to the actual correctness gate (tests), not just genuinely non-blocking checks | Silently converts the one stage built to catch real bugs into a no-op                                                            |
| Leaving a temporary override in place with no removal plan or ticket                                        | The override outlives its original justification and becomes a permanent, invisible gap                                          |
| Rebuilding the artifact separately for each environment                                                     | Reopens the exact drift risk artifact promotion exists to close — staging and production may no longer be running the same thing |
| Deciding how rollback works only after a bad deploy is already live                                         | Slower, riskier, and less reliable than a rollback path designed and rehearsed in advance                                        |
| Treating pipeline configuration changes as lower-stakes than application code                               | A deploy-gate change can have a larger blast radius than most feature code, and deserves matching review rigor                   |
