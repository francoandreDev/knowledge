Two engineers each spent a week writing a proposal for the three bets from

**When two well-reasoned proposals disagree on order, the useful question
is not "who is right" but "which inputs did each one weigh, and which did
it leave out?"**

## What inputs does a sequencing decision need?

Neither proposal is wrong. Each optimises a real input and under-weights
another:

| Input            | Question it answers                                 | Proposal A | Proposal B |
| ---------------- | --------------------------------------------------- | :--------: | :--------: |
| Business context | What is the company betting on this year?           |    High    |    Low     |
| Current pain     | What is costing money or trust right now?           |   Medium   |   Medium   |
| Org capacity     | How many bets can run at once without stalling all? |  Missing   |  Missing   |
| Dependency graph | Which bets make other bets cheaper or safer?        |    Low     |    High    |

Both skip **org capacity**, which is the input that turns "here is an
order" into "here is what happens in quarter one versus quarter three".

<Checkpoint question="Proposal A leads with SOC 2 because a deal depends on it. Proposal B leads with the split because billing gets cheaper after it. Is one of those inputs simply more important in general?">

No. Both are real costs, denominated differently: lost revenue if the deal
slips, duplicated engineering work if billing is built twice. A defensible
decision puts both on one table and states the trade-off: "we accept this
risk of the deal slipping to avoid that cost of rebuilding billing."
Silently favouring the input the author weighed by instinct is the failure.

</Checkpoint>

## How does a dependency change a bet's real cost?

**If billing can start without the split, why does the split go first?**
Because starting is not the same as being cheap. Billing built against the
tangled monolith has to be rebuilt once the split moves its data:

```mermaid
flowchart LR
    A["Split the monolith"] -->|"makes cheaper"| B["Event-driven billing"]
    A -.->|"not required for"| C["SOC 2 compliance"]
    B -->|"supplies a cleaner audit trail"| C
```

The split is first on the roadmap not because it is the most urgent, but
because skipping it adds a rebuild cost to the bet after it. Note the
dotted line: SOC 2 does not need the split, so nothing forces it to wait.

## How are bets staged into Now, Next and Later?

Bets are not all committed with the same confidence. The further out a bet
sits, the less certain its timing should be:

```mermaid
gantt
    title Two-year technical roadmap, first draft
    dateFormat  YYYY-MM-DD
    axisFormat  %Y-%m
    section Now
    Monolith split, phase 1            :active, a1, 2026-01-01, 6M
    section Next
    Event-driven billing               :a2, after a1, 9M
    SOC 2 controls and audit prep      :a3, 2026-07-01, 6M
    section Later
    Monolith split, phase 2            :a4, after a2, 6M
```

| Horizon | Commitment                               | Can still change?           |
| ------- | ---------------------------------------- | --------------------------- |
| Now     | A team is staffed on it this quarter     | Rarely                      |
| Next    | Planned, order and scope not locked      | Yes, based on how Now lands |
| Later   | Directional, shows the shape of the plan | Expected to change          |

SOC 2 starts in Next, not after the whole split. Dependency reduction
decided which bet goes first, not that everything else must wait.

<Checkpoint question="A stakeholder asks why SOC 2 work starts in Next instead of waiting until the split is completely finished. What is the answer?">

Now and Next are a confidence horizon, not a strict queue. The split was
placed first because it lowers the cost of the billing work, not because
every bet depends on it. SOC 2 has no such dependency, so it can run in
parallel once capacity allows. It sits in Next because its own scope is
still firming up, not because it is waiting in a single-file line.

</Checkpoint>
