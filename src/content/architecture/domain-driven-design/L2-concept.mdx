## Why is the aggregate a modeling decision, not a database feature?

**A database already offers transactions, row locks and constraints. Why
is none of them the aggregate?** Because they enforce _mechanics_
(atomic commit, uniqueness, isolation), while an aggregate answers a
different question: which facts must be checked together, every time?
Only the domain knows that "items, total and limit belong together".
The aggregate is that answer; the repository then uses the database's
tools to persist it safely.

```mermaid
flowchart TB
    subgraph Aggregate["Order aggregate: one consistency unit"]
        Root["Order (root)"]
        L1e["OrderLine 1"]
        L2e["OrderLine 2"]
        Root --> L1e
        Root --> L2e
    end
    Cust["Customer: separate aggregate,<br/>referenced by CustomerId only"]
    Aggregate -. "credit limit passed in<br/>as a value, not a live join" .-> Cust
```

**Why is `Customer` outside, when the check needs its credit limit?**
`Customer` has its own rules and its own write traffic. Putting it inside
`Order` would make every order write contend with every customer edit.
The boundary encloses the _smallest cluster that must be consistent on
every write_, and `Order` only needs the limit as an input value.

<Checkpoint question="A teammate says every order write already runs inside a database transaction, so Order #4471's bug cannot happen. What is missing from that claim?">

A transaction makes one write atomic. It never decides which combined
facts may be true together. Clerk A and Clerk B each wrote atomically,
and the rule "total at most the limit" was still not enforced anywhere.
That rule needs an aggregate root that checks it on every change.

</Checkpoint>

## Does this thing need an identity?

**Line 7 changes quantity from 2 to 3. Is it still line 7?** Yes, so
the line is an **entity**: its identity persists across changes. **Two
separate `$10` amounts: are they the same $10, or merely equal?** Merely
equal, so money is a **value object**: immutable, compared by contents,
replaced rather than edited.

| Question                                    | Entity                | Value object                      |
| ------------------------------------------- | --------------------- | --------------------------------- |
| Does "which one, exactly" matter?           | Yes, tracked by an id | No, only "what does it equal"     |
| Can it change and stay the same thing?      | Yes                   | No, a change produces a new value |
| Identical fields: same thing or just equal? | Different things      | The same, by definition           |

Getting it backwards costs real effort. Modeling `Money` as an entity adds
identity tracking nothing needs. Modeling a line as a value object makes
"update line 7" impossible to say, because every edit yields a different
object.

## Domain events: who tells Billing, and when?

**`placeOrder()` must tell Billing and Fulfillment. Should it call them
directly?** No. That would make `Order` depend on every downstream
context being up and shaped a certain way. Instead the root _records_ a
fact, `OrderPlaced`, and the application layer publishes it after the
save commits.

```mermaid
sequenceDiagram
    participant App as Application layer
    participant Order as Order root
    participant Repo as OrderRepository
    participant Bus as Event publisher
    App->>Order: placeOrder()
    Order->>Order: check rules, set PLACED, record OrderPlaced
    App->>Repo: save(order)
    Repo-->>App: committed
    App->>Bus: publish(order.pullDomainEvents())
    Bus-->>Billing: OrderPlaced
    Bus-->>Fulfillment: OrderPlaced
```

**Why after the commit and not the moment the event is recorded?** If the
save then fails, Billing has already been told about an order that does
not exist. Publishing after the commit means the event is only ever true.
One gap remains: a crash between the save and the publish loses the
event. L3 covers the usual fix, an outbox.

<Checkpoint question="The save fails on a constraint violation right after placeOrder() recorded OrderPlaced. Under the publish-after-commit rule, what does Billing receive?">

Nothing. The event was only recorded inside the aggregate; it is
published when `save` has succeeded. If the save fails, the recorded
event is discarded with the failed attempt, so Billing never hears about
an order that was never stored.

</Checkpoint>

## Where does a context boundary live in code?

**With several contexts, is the boundary a folder, a package, or a
service?** All three at different stages. The context map says which
relationship governs each edge:

| Relationship                             | What it looks like in code                                                          | Fits when                                                           |
| ---------------------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| Anticorruption layer                     | An adapter module at the boundary translating the other model into yours            | The other model carries different meanings you must not absorb      |
| Conformist                               | Downstream uses the upstream shape directly, no translation                         | You have no leverage over the upstream, such as a third-party API   |
| Customer-supplier                        | Upstream accepts downstream needs through a ticket queue or contract tests          | Both teams answer to one organization and can prioritize each other |
| Open host service and published language | Upstream exposes one stable, versioned contract instead of many custom integrations | Many downstream contexts need the same data                         |

```mermaid
flowchart LR
    subgraph OrderCtx["Order Management"]
        OrderAgg["Order aggregate"]
    end
    subgraph BillingCtx["Billing"]
        Bill["Invoice aggregate"]
    end
    subgraph Legacy["Legacy stock system: no leverage"]
        Rows["Flat stock rows"]
    end
    OrderAgg -- "OrderPlaced: versioned event schema" --> BillingCtx
    Rows -- "adapt, do not negotiate" --> ACL["Anticorruption layer"] --> OrderAgg
```

**Why name the relationship instead of calling every edge "an API"?**
Each implies a different failure when misjudged. Treating a conformist
edge as customer-supplier means filing requests a vendor will never read.
Treating a customer-supplier edge as conformist means silently absorbing
breaking changes you had standing to negotiate.
