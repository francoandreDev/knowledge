**Dana is a backend engineer at Boxtree, a mail-order retailer. Product wants
one thing added to `calculateOrderTotal`: a loyalty-tier discount (bronze /
silver / gold) that stacks on top of the existing member discount. The
function that has to hold this new logic is 68 lines long, four levels deep
in places, and computes "is this a real member" three separate times with
three slightly different conditions. Dana has two honest options: wedge one
more `if` into the mess and ship today, or spend time first making the
function safe to change. Under a deadline, option one always looks faster.**

Is it? The if/else Dana is tempted to add doesn't go into empty space — it
goes into a function that's already this tangled, and every future change to
it inherits that same cost, compounding. The question this unit answers
isn't "how do I add this discount" — it's "how do I change code that's
already hard to change, without adding to the mess or breaking something
that currently works."

## What "refactoring" actually means

**Refactoring** is changing a program's internal structure — how the code is
organized — **without changing what it does from the outside.** Same inputs
produce the same outputs, every time, before and after. That single
constraint is the whole discipline:

|                       | Refactoring                          | Rewriting                              |
| --------------------- | ------------------------------------ | -------------------------------------- |
| Observable behavior   | Unchanged, by definition             | Usually changes, at least temporarily  |
| Step size             | Tiny, individually verifiable        | Large, often "big bang"                |
| Safety net needed     | Tests you already trust              | New tests, written from scratch        |
| Can you stop halfway? | Yes — every step leaves working code | Rarely — halfway is often broken       |
| What it fixes         | How hard the code is to read/change  | What the code does, structure included |

If you can't answer "what did this change do to behavior?" with "nothing,
provably," you're not refactoring — you're doing something riskier, even if
the code looks tidier afterward. That distinction matters because the two
call for completely different amounts of caution.

## Why the safety net comes before the tidying

A refactor's whole claim is "behavior didn't change." **Without an automated
test suite already covering that behavior, that claim is just an opinion.**
No tests doesn't mean "be extra careful" — it means the safe move isn't
available yet. The actual first step, before touching a single line of the
tangled function, is writing tests that pin down what it currently does
(including its quirks) so any later step has something to check itself
against.

## Code smells: symptoms, not sentences

A **code smell** is a surface signal that a design problem probably lives
underneath it — not proof, and not a rule that the code must be rewritten on
sight. Boxtree's function shows several at once:

| Smell            | What it looks like                                 | Why it costs you                                              |
| ---------------- | -------------------------------------------------- | ------------------------------------------------------------- |
| Duplicated logic | The same check/calculation, written more than once | Fix a bug in one copy, the other keeps the old behavior       |
| Long function    | Does many unrelated things in one block            | Hard to hold the whole thing in your head to change one part  |
| Deep nesting     | `if` inside `if` inside `if`                       | Each new branch multiplies the paths you have to reason about |
| Magic numbers    | `0.07`, `75`, `1.5` with no name                   | The next reader has to guess what each one means and why      |

None of these are wrong on their own in small doses — a smell is a prompt to
look closer, not an automatic rewrite order. The rest of this unit is about
what to do once you've decided a smell is worth acting on: small, reversible
steps, verified at every single one, never mixed with an actual behavior
change.
