Sam writes a shipping-cost function for a small checkout app: domestic orders
get a flat rate, international orders get the flat rate plus a customs fee.
Six lines, two branches, nothing else planned. A reviewer comments: "Use the
Strategy pattern. It's best practice for anything with conditional logic."
**Should Sam do it? And what would you need to know about this code to
answer, other than the fact that it contains an `if`?**

The question is not "is Strategy a good pattern?" It is whether this code has
the problem Strategy exists to solve. If it does not, the pattern replaces
six readable lines with four new types and the same logic, spread thin.

## What is a design pattern, if it is not a rule?

**If two engineers say "make it a Strategy", what did they just agree on?**
A shape, not a block of code: a named, reusable arrangement of types that
solves a recurring structural problem. The name is shorthand so nobody has to
re-explain the whole arrangement.

The catalog most people mean comes from the 1994 book _Design Patterns_ (the
"Gang of Four"), which named 23 patterns in three families:

| Family         | What it is about                       | Examples                           |
| -------------- | -------------------------------------- | ---------------------------------- |
| **Creational** | How objects get built                  | Factory Method, Singleton, Builder |
| **Structural** | How objects are composed together      | Adapter, Decorator, Facade         |
| **Behavioral** | How objects communicate and share work | Strategy, Observer, Command        |

Each pattern exists to solve one specific recurring problem. None exists to
make code look more polished, and that framing is the trap this unit is about.

## What goes wrong when a pattern is used as a badge?

- **Cargo-culting** means copying the visible shape of a practice without the
  conditions that made it work. The name comes from islanders who built
  runway-shaped structures after seeing cargo planes land at airstrips: the
  shape was reproduced, the reason was not.
- **Résumé-driven design** means choosing a pattern because it looks good to
  have used, not because the problem asks for it.

Both produce code that looks like best practice and is harder to read, test
and change than the plain version it replaced.

Every pattern trades a direct solution for an indirect, flexible one. That
trade only pays off when the flexibility is used:

| Cost                  | What it looks like                                                |
| --------------------- | ----------------------------------------------------------------- |
| More files and types  | 1 function becomes 1 interface + N classes + a factory            |
| More indirection      | Following the logic means jumping through an extra layer          |
| Slower onboarding     | A new reader learns the shape before they can read the logic      |
| Premature abstraction | The flexible seam may not match how the code really changes later |

Sam's calculator has 2 branches, no third planned and nothing to swap at
runtime. Strategy would pay every cost in that table and collect nothing. That
does not make Strategy bad; it makes this not its problem. L2 builds the test
for telling the two cases apart, and L3 shows a second scenario where the same
pattern is the right call.

## Key terms

- **Design pattern** — a named, reusable shape for a recurring structural
  problem; a vocabulary word, not a mandate.
- **Cargo-culting** — reproducing a practice's shape without the conditions
  that made it useful.
- **Résumé-driven design** — choosing a solution for how it looks on paper.
- **Indirection** — an extra layer between "what calls this" and "what runs";
  patterns buy flexibility with it.
- **Axis of variation** — a dimension along which behavior really differs and
  keeps changing, such as which payment processor or which shipping region.
