**Sam ships a shipping-cost calculator at Widgetly, a checkout platform. It's
one function with a six-line if/else: domestic orders get a flat rate,
international orders get a flat rate plus a customs fee. Nothing else is
planned. In review, Priya — a senior engineer — leaves a comment: "This
should use the Strategy pattern. It's best practice for anything with
conditional logic." Sam isn't sure whether to push back or just do it — after
all, isn't using named patterns what separates a junior implementation from a
senior one?**

It's the wrong question. The right one is: does this if/else have a real
problem that a pattern would fix, or would the pattern just replace six lines
with four files and the same six lines of logic, spread out and harder to
follow? A design pattern is a tool for a specific kind of problem — not a
badge of seniority to sprinkle on code that doesn't have that problem yet.

## What a design pattern is

- A **design pattern** is a named, reusable _shape_ for solving a
  recurring structural problem — not a block of code you copy-paste, and
  not a requirement. The name is a shorthand two engineers can use in
  conversation ("just make it a Strategy") instead of re-explaining the
  whole shape every time.
- The catalog most people mean by "design patterns" comes from the 1994
  book _Design Patterns: Elements of Reusable Object-Oriented Software_
  (the "Gang of Four" — Gamma, Helm, Johnson, Vlissides), which named 23
  patterns split into three families:

| Family         | What it's about                                  | Examples                           |
| -------------- | ------------------------------------------------ | ---------------------------------- |
| **Creational** | How objects get built                            | Factory Method, Singleton, Builder |
| **Structural** | How objects are composed/wired together          | Adapter, Decorator, Facade         |
| **Behavioral** | How objects communicate and share responsibility | Strategy, Observer, Command        |

- Every pattern in that catalog exists to solve a **specific** recurring
  problem. None of them exist to make code "look more professional" — that
  framing is exactly the trap this unit is about.

## The failure mode: cargo-culting a pattern

- **Cargo-culting** — copying the visible _shape_ of a practice without
  the underlying conditions that made it work, then expecting the same
  result. Named for Pacific islanders who, having seen cargo planes land
  near WWII airstrips, built runway-shaped structures out of straw hoping
  planes would land again — the shape was reproduced, the reason for it
  wasn't.
- **Résumé-driven design** — choosing a pattern (or a technology) because
  it looks good to have used, not because the problem calls for it.
- Both produce the same symptom: code that _looks_ like it follows best
  practices, while actually being harder to read, harder to test, and
  harder to change than the plain version it replaced — because the
  pattern's cost was paid without the problem that earns it back.

## The cost side nobody mentions

Every pattern in the catalog trades a **direct, obvious** solution for an
**indirect, flexible** one. That trade is only worth making when the
flexibility is actually used. The cost side is real and always present:

| Cost                  | What it looks like                                                              |
| --------------------- | ------------------------------------------------------------------------------- |
| More files/types      | 1 function → 1 interface + N classes (+ a factory)                              |
| More indirection      | Following the logic means jumping through an extra layer                        |
| Slower onboarding     | A new reader has to learn the pattern's shape before the actual logic           |
| Premature abstraction | The "flexible" seam might not match how the code actually needs to change later |

Sam's shipping calculator has 2 branches, no roadmap for a third, and no
requirement to swap logic at runtime. Priya's proposed Strategy pattern
would pay every cost in that table for zero benefit gained. That doesn't
mean Strategy is a bad pattern — it means this isn't its problem. L2 builds
the checklist for telling the two cases apart, and L3 shows a second,
real scenario (payment processing at the same company) where the exact
same pattern **is** the right call.

## Key terms

- **Design pattern** — a named, reusable shape for a recurring structural
  problem; a vocabulary word, not a mandate.
- **Cargo-culting** — reproducing a practice's visible shape without the
  conditions that made it useful.
- **Résumé-driven design** — choosing a solution for how it looks on paper,
  not for what the problem needs.
- **Indirection** — an extra layer of abstraction between "what calls this"
  and "what actually runs" — patterns are, structurally, ways of buying
  flexibility with indirection.
- **Axis of variation** — a dimension along which behavior genuinely
  differs and changes over time (e.g. "which payment processor," "which
  shipping region") — the thing a pattern like Strategy is meant to
  isolate.
