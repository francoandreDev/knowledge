A `MonthlyReportGenerator` fetches usage data, calculates billing totals and
renders a PDF. All three steps "belong to generating the report", yet each
answers to a different change: a new usage-tracking system, a new pricing tier,
a rebrand. They sit as adjacent lines in one method, and nothing marks which
lines are safe to touch for which request.

**If a rebrand landed tomorrow, which lines would an editor have to scroll past
to make it, and which of those could cost real money if touched by accident?**

## What actually caused the incident?

A designer requests a rebrand. An engineer edits the PDF-layout lines of
`generate()`. In the same scroll, a stray edit changes the adjacent billing
line from `0.001` to `0.01` for `api_call` events. That is a factor of
10 (0.01 / 0.001). The rebrand ships; two weeks later finance sees API-call
billing ten times too high for every customer that month.

**The root cause is not the typo.** Mistakes happen. The root cause is that a
layout-only change required editing a method that also held financially
sensitive billing logic, close enough to touch by accident and with no test
isolating it from layout work.

<Checkpoint question="The engineer never intended to touch billing. Would adding a review checklist item ('did you mean to change the billing line?') have reliably prevented the bug?">

Not reliably. A checklist depends on a reviewer noticing one unrelated line
inside a diff that is mostly about layout, which is exactly the kind of small
edit that slips past review. A checklist adds a chance of catching it;
separating the responsibilities into different files removes the opportunity
for it to appear in the same diff at all. That is the difference between a
process fix and a structural fix: the root cause is that billing was reachable
from a layout-only change, and only a structural boundary removes that.

</Checkpoint>

## How does the risk scale with the number of responsibilities bundled?

**Is one extra bundled concern a small problem or a growing one?** Assume each
responsibility takes 5 lines, as in the scenario. For an edit to any one
responsibility, the unrelated share of the method is (n − 1) / n lines for n
bundled:

```mermaid
xychart-beta
    title "Share of the method unrelated to any one edit (%)"
    x-axis "Responsibilities bundled into one method" [1, 2, 3, 4, 5]
    y-axis "Unrelated lines (%)" 0 --> 100
    bar [0, 50, 66.7, 75, 80]
```

At one responsibility there is nothing unrelated to hit, so the risk is
structurally zero. At three, the incident's shape, two thirds of the method is
irrelevant to any single request. The slider demo on this page lets you vary
both the number of bundled concerns and the lines each one takes; the share
depends only on the count, which is why the answer to a bigger method is not
"be more careful" but "bundle fewer reasons".

## What does the split change?

```mermaid
flowchart TD
    subgraph Before["Before: one shared method"]
        M["generate()"] --> F1["fetch usage"]
        M --> C1["calculate billing"]
        M --> R1["render PDF"]
    end
    subgraph After["After: a rebrand touches one unit"]
        G["generate(): orchestrates only"] --> UF["UsageDataFetcher"]
        G --> BC["BillingCalculator"]
        G --> RR["ReportPdfRenderer: rebrand edits land here only"]
    end
```

| Unit                | Its one reason to change            | Has its own tests for              |
| ------------------- | ----------------------------------- | ---------------------------------- |
| `UsageDataFetcher`  | How usage data is stored or queried | Query results for an account/month |
| `BillingCalculator` | Pricing rules                       | Rates, directly, with fixed events |
| `ReportPdfRenderer` | Layout and branding                 | Output structure                   |
| `generate()`        | Order or composition of the steps   | That the three steps are called    |

The rebrand now edits `ReportPdfRenderer` only. The rate logic is in another
file, not visually adjacent, and protected by a test that pins `api_call` to
its rate. A layout pull request would not touch it, and if it did, that test
would fail.

<Checkpoint question="generate() still calls all three units in sequence. Does it secretly still own all three responsibilities, just spread across calls?">

No. Its one responsibility is orchestration, and its reason to change differs
from any of theirs: it changes if the _sequence or composition_ of steps
changes (a fourth step, or caching the fetch), not if a rate or a font size
changes. Calling into other units is not the same as owning their logic.

</Checkpoint>

## What happens to the next request, and can you write it?

The rebrand is one case, not the whole territory. **What if the next request is
"add an enterprise pricing tier": does the split hold, and which unit absorbs
the change?** Only the billing calculator changes, because only the rate lookup
changes:

```mermaid
flowchart LR
    Req["Enterprise tier request"] --> BC["BillingCalculator: rate lookup"]
    BC -. untouched .-> UF["UsageDataFetcher"]
    BC -. untouched .-> RR["ReportPdfRenderer"]
```

Here code is the clearest vehicle, because the claim is "the whole change fits
in one small function". Using whole cents per unit so no floating-point
rounding is involved:

```js
function calculateTotal(usageEvents, tier) {
  const cents =
    tier === "enterprise"
      ? { api_call: 1, storage: 4 }
      : { api_call: 2, storage: 5 };
  return usageEvents.reduce((sum, e) => sum + e.quantity * cents[e.type], 0);
}
```

The rate table is the only thing that moved. The fetcher and renderer do not
know tiers exist.

**Now extend it yourself.** What if the request were "the usage system moves to
a new event schema", or "finance wants a CSV export beside the PDF"? Which unit
absorbs each? And what would you have to believe about the team (who owns what,
how often each changes) before deciding that a CSV export deserves its own
renderer instead of a flag on the existing one? The worked example shows the
method; the answer in your codebase depends on its real change patterns.

## Failure modes

| Failure mode                                        | What it gets wrong                                                                                                                                                             |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Believing the split alone prevents the bug          | It reduces the chance of an accidental cross-responsibility edit, but does not make it impossible. Real protection is separation plus a billing test that catches a wrong rate |
| Splitting only reactively, after an incident        | The reasons-to-change test from L2 could have flagged the violation in the original review, before anything shipped                                                            |
| Over-rotating into splitting everything defensively | The lesson is "split along genuinely independent reasons", not "prefer more, smaller classes"; the overcorrection reintroduces cost with no matching benefit                   |
| Assuming this class of bug is rare                  | Editing unrelated code that sits nearby is an easy, common mistake, which is why boundaries are a structural safeguard and not an aesthetic preference                         |
