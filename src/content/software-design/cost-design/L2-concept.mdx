Two teams build the same order-confirmation feature. Team A's order code
reaches into the mailer's internal connection object and sends the message
itself. Team B's order code just calls `notifier.notify(order)` on whatever it
was given. Both pass review, both pass every test, both ship this week.

**If both do the same thing today, what question would tell you which design
is better, and why can't "does it work" answer it?**

## What actually makes Team A riskier than Team B?

Neither has a bug today. The difference is the **surface a future, unrelated
change could break**.

```mermaid
flowchart LR
    subgraph A["Team A: high coupling"]
        OA["Order code"] -->|"uses internal connection"| MA["Mailer internals"]
    end
    subgraph B["Team B: low coupling"]
        OB["Order code"] -->|"notify()"| IB["Stable interface"]
        IB --> MB["Mailer internals"]
    end
```

In pseudocode, the whole difference is one line:

```text
Team A:  mailer.connection.send_raw(build_message(order))   # depends on internals
Team B:  notifier.notify(order)                             # depends on a promise
```

Team B is not better because it is shorter. The set of mailer changes that
could break the order code shrank from "almost anything" to "changing what
`notify()` means", a small and deliberate surface.

<Checkpoint question="Team C's order code calls only notify(order), but the class behind notify() imports and calls into three unrelated internal services. Has Team C achieved low coupling?">

Between the order code and the notifier, yes. But coupling is a property of
every relationship in the system, not just the one you checked. The notifier
reaching into three unrelated services is Team A's mistake one layer deeper:
a change to any of those services can still ripple outward, passing through
the notifier first. A narrow interface at one boundary says nothing about the
boundaries behind it.

</Checkpoint>

## Is a module cohesive just because its parts touch the same data?

**Two methods both read the same order. Does that make them belong together?**
No. The test is whether they would ever change for the same reason.

```mermaid
flowchart TD
    subgraph LOW["Low cohesion: one class, three reasons to change"]
        P["OrderProcessor"] --> T["price rules change"]
        P --> E["email wording changes"]
        P --> L["analytics format changes"]
    end
    subgraph HIGH["High cohesion: split by reason to change"]
        PC["PricingCalculator"] --> T2["price rules change"]
        ON["OrderNotifier"] --> E2["email wording changes"]
        AL["AnalyticsLogger"] --> L2["analytics format changes"]
    end
```

Pricing, email wording and analytics format are three independent reasons to
change code. Bundled in one file, an edit for any one of them risks breaking
the other two, purely because they share a file.

<Checkpoint question="A developer splits OrderProcessor into three classes, but each one still reaches into the other two to share state. Did the split help?">

It raised cohesion inside each class, since each now has one reason to
change. But reaching across the new classes brought coupling back, the same
kind Team A had. The two are separate measurements, not opposites you trade:
a real improvement splits by reason to change and then lets the pieces talk
through narrow interfaces.

</Checkpoint>

## How do the two properties bend the cost curve?

**Why do early changes cost the same under both designs, and later ones
don't?** Every future change must (1) work out what else it might affect, and
(2) touch only what is relevant.

| A change must…                 | Harder under… | Because…                                           |
| ------------------------------ | ------------- | -------------------------------------------------- |
| Find out what else might break | High coupling | Dependents reach past the interface into internals |
| Touch only what is relevant    | Low cohesion  | Unrelated logic is tangled into the same unit      |

Here is the effect as a model, using the unit's own demo formula: the first
change costs 2 hours, and under the coupled design each later change costs 15%
more than the one before (an assumed penalty, not a measurement).

```mermaid
xychart-beta
    title "Cumulative hours after N changes (model: 2h first change)"
    x-axis "Changes made" [1, 5, 10, 15, 20]
    y-axis "Cumulative hours" 0 --> 210
    line "No coupling penalty" [2, 10, 20, 30, 40]
    line "15% penalty per change" [2, 13.48, 40.61, 95.16, 204.89]
```

The lines are almost together at the start, which is why bad design is easy
to miss. Coupling and cohesion do not cause bugs directly; they multiply the
cost and risk of every later change.
