You build a bridge out of toothpicks. You put one coin in the middle of a 10 cm
span and it sags a little. Passed: the bridge holds. Your friend wants the
same bridge 15 cm long and says, "Half again as long, so it should sag about
half again as much."

Your single test cannot say whether they are right, because you only tested
the 10 cm bridge. **What tool tells you what the 15 cm bridge will do before
you build it?**

## What does a passing test actually tell you?

A passing test, type check or compiler run answers one question: **does this
thing do what it claims in the case I tried?** The bridge you tested is fine.
The longer bridge was never tested, so the test is silent about it.

| Question                                   | Tool that answers it            |
| ------------------------------------------ | ------------------------------- |
| Does this code do what it claims?          | Tests, type checker, compiler   |
| What happens in a case I have not run yet? | A model: a formula plus numbers |

For software, the untried case is usually bigger: more traffic, more users,
more data, more time. Math used as **prediction** takes a relationship you
trust, plugs in the numbers you have, and tells you what to expect at the
scale you have not reached.

## Is this the same as estimating on the back of an envelope?

Close, but different. **Fermi estimation** (see `applied-math/orders-magnitude`)
gets you a rough order of magnitude with almost no data. This unit is for the
moment after that, when you do have real numbers and a known relationship.

```mermaid
flowchart LR
    A["No data yet:<br/>about how big is this?"] -->|"Fermi estimate"| B["Order of magnitude"]
    C["Real numbers in hand:<br/>what happens as this grows?"] -->|"Known formula"| D["A specific, checkable number"]
```

## Why does "50% bigger, so 50% worse" keep failing?

The friend's guess is a **linear guess**: change the input by some
percentage and assume the result changes by the same percentage. Many real
relationships are not linear. For a simple beam held at both ends with a
weight in the middle, the standard result is that sag grows with the cube of
the length:

$$sag \propto length^3$$

Only the ratio matters here. A bridge 1.5 times as long sags $$1.5^3 = 3.375$$
times as much, not 1.5 times. That is the 3.4 mm in the callout above.

Software has the same trap. If 10 users can each message each of the other 9,
that is `10 x 9 = 90` possible conversations. At 100 users it is
`100 x 99 = 9,900`. Users grew 10 times; conversations grew 110 times.

## What this unit covers

- **Correctness math vs. predictive math**: tests cover the cases you tried;
  a formula covers the ones you did not.
- **Known formula vs. Fermi estimate**: estimate when you have no data, use a
  formula when you do.
- **The linear trap**: ask what is being counted before assuming that twice
  the input means twice the result.
- **Two worked tools in L2/L3**: Little's Law (how many things are inside a
  system at once) and the wait-time curve near full capacity.
