Priya finishes the login fix and emails `project-v2-FINAL.zip` to Alex. Alex,
working from an older copy he'd already unzipped, makes an unrelated tweak and
saves his own folder back as `project-v2-FINAL-REAL.zip` — without ever
opening Priya's file. Two hours later, nobody can say which zip has both
fixes. Priya's login change is simply absent from Alex's copy: no message
explaining why, no diff showing what's different, no record of when it went
missing.

**Both files are named "final." Neither is complete, and there's no way to tell that from the filenames alone. What information would you need to have been recorded automatically, at the moment each save happened, to answer any of the three questions above?**

The answer version control gives: record every save as a labeled, comparable,
permanent snapshot — automatically, not by hand.

## Why can't manual copies answer the three questions?

Git does **not** record every time you press Save in your editor. Saving changes the file on disk. Git records a checkpoint only when you deliberately build one with `git add` and `git commit`. That deliberate checkpoint is what becomes comparable, nameable, and recoverable later.

| Question a zip file can't answer   | What Git records instead                               |
| ---------------------------------- | ------------------------------------------------------ |
| Why did this change?               | A commit message, written at the moment of the change  |
| Which copy has both people's work? | Parent links, and a merge commit that joins two lines  |
| Exactly when did the bug appear?   | An ordered chain of commits you can inspect one by one |

Manual copies fail on all three at once: no record of _why_, no safe way to combine two people's edits, and no way to find the exact moment a bug arrived. Renaming files more carefully does not fix this, because the missing thing is not a better name. It is a recorded **relationship** between one saved state and the next.

## What is a commit, and what links one to the next?

A **commit** is an immutable snapshot of the whole project plus metadata: who made it, when, why (the message), and a pointer to the commit before it. That pointer is the **parent link**, and the chain of parent links is the entire history. A zip file has no such pointer, which is exactly why Alex's copy and Priya's copy are two dead ends.

```mermaid
flowchart LR
    A["Commit A"] -->|parent pointer| B["Commit B"]
    B -->|parent pointer| C["Commit C (HEAD)"]
    A -.no such link exists.-> Z1["project-v1.zip"]
    B -.no such link exists.-> Z2["project-v2-FINAL.zip"]
```

Because every commit points to its parent, you can walk backward to _any_ past state, not just undo the last action. Git stores a **full snapshot** per commit rather than a list of edits; unchanged files are not re-copied but referenced by content (L2 shows how). A file Git knows about is **tracked**; one it can see but you have not promised to include is **untracked**.

## What are branches, and what does "distributed" add?

Priya and Alex both started from the same past state. Git remembers that shared starting commit, so it can later ask "what did Priya change from the base, and what did Alex change from the same base?" and combine the answers. The `merge` unit teaches that mechanism; here the point is that manual folders never preserve the relationship.

```mermaid
gitGraph
    commit id: "base"
    branch priya
    commit id: "login fix"
    checkout main
    branch alex
    commit id: "unrelated tweak"
    checkout main
    merge priya
    merge alex
```

A **branch** is just a movable label pointing at a commit. Creating one copies no files, so it is instant. **Distributed** means every clone carries the _entire_ history, not only the latest snapshot: no single point of failure, and you can commit, branch, and read history offline.
