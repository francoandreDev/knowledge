An engineer runs `git pull` on Monday — it finishes cleanly, no extra
commits, history stays a straight line. On Tuesday, the exact same
command on the exact same branch adds a new commit nobody wrote:
"Merge branch 'main' of ...". **Same command, same person, same repo.
What changed between Monday and Tuesday that made git decide a new
commit was needed this time?**

</Scenario>

## The shape of the problem

- `git pull` is really two steps combined: fetch the remote's latest
  commits, then reconcile them with local history — and _how_ it
  reconciles depends entirely on whether local history has moved since
  the two last agreed on a common point.
- When local and remote have both added commits since they diverged,
  git can't just "add the new stuff" — it has to decide how to combine
  two different, real sequences of change, and a merge commit is one
  specific way of recording that decision, not the only one.

## Key terms

- **Fast-forward** — when the local branch's current commit is a
  direct ancestor of the remote's commit, so incorporating the remote's
  changes just means moving the local pointer forward — no new commit
  needed, no reconciliation required.
- **Merge commit** — when local history has diverged from remote (both
  sides added commits since the common point), git creates a new
  commit with two parents to record that both histories are now
  combined.
- **Rebase** — instead of creating a merge commit, replaying local
  commits one by one on top of the remote's latest commit, producing a
  straight-line history as if the local work had started from there in
  the first place.
- **Divergence** — the state where local and remote both have commits
  the other doesn't, counted from their last common ancestor — this is
  exactly the condition that makes a fast-forward impossible.

## What this unit covers

L2 works through exactly when a fast-forward is possible versus when
divergence forces a real reconciliation, and what merge and rebase each
actually do differently with the same diverged history. L3 implements
both a real ancestor-check function and a real rebase operation on an
actual commit graph, to show precisely why Monday's pull stayed clean
and Tuesday's didn't.
