A production bug appears with no obvious cause. An engineer runs `git
bisect`, which does exactly what it's supposed to do — it correctly
narrows the search down to a single commit. That commit is titled
"various fixes and cleanup" and touches 14 files, bundling a dozen
unrelated changes made over an afternoon. Finding the actual line
responsible still takes two more hours of manually reading the diff.
**`git bisect` did its job. Why didn't that actually solve the
problem?**

</Scenario>

## The shape of the problem

- `git bisect` finds the _commit_ where a problem was introduced — it
  has no way to find the specific _change_ within that commit, if the
  commit bundles more than one unrelated change together.
- A commit that mixes several unrelated changes is exactly as easy to
  create as a commit that contains one — nothing stops it from
  happening, and it often feels more efficient in the moment to batch
  everything from a work session into one commit.
- The fix isn't a smarter version of `git bisect` — it's committing in
  a way that keeps `git bisect`'s answer actually useful: one logical
  change per commit, so finding _the commit_ is the same as finding
  _the change_.

## Key terms

- **Atomic commit** — a commit that contains exactly one logical
  change, complete and coherent on its own, not a bundle of several
  unrelated edits made in the same sitting.
- **Conventional commits** — a commit message format
  (`type: short description`, e.g. `fix: correct off-by-one in
pagination`) that states plainly what kind of change a commit makes,
  making history scannable without opening every diff.
- **git bisect** — a command that performs a binary search over commit
  history, narrowing down which commit introduced a bug by repeatedly
  testing a midpoint commit and asking "good or bad?"
- **Binary search** — the algorithm underneath `git bisect`: at each
  step, eliminate half of the remaining candidates by testing the
  midpoint, which is what makes it fast even across a large history.

## What this unit covers

L2 works through exactly how `git bisect`'s binary search operates,
what conventional commit types look like, and why atomic commits are
what makes bisect's answer actually actionable. L3 implements the
binary search itself in real code, runs it against both an atomic
commit history and a bundled one, and measures precisely where the
bundled version's usefulness breaks down.
