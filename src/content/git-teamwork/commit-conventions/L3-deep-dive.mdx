## Implementing bisect as binary search

Before the code, trace the idea by hand. Suppose commits `c0` through
`c7` are in order, `c0` is known good, and `c7` is bad:

| Step | Remaining possible first-bad range | Test midpoint | If midpoint is good | If midpoint is bad |
| ---- | ---------------------------------- | ------------- | ------------------- | ------------------ |
| 1    | `c1` through `c7`                  | `c3`          | Search `c4..c7`     | Search `c1..c3`    |
| 2    | Half of the previous range         | midpoint      | Keep upper half     | Keep lower half    |

In the code, `lo` and `hi` are array indexes marking the current
edges of that shrinking search range. They are not commit hashes
themselves; they are positions in the `commits` array.

```js
// commits: an array of commit ids, oldest first
// isBad(commitId): simulates "run tests at this commit" -> true if broken
function bisect(commits, isBad) {
  let lo = 0; // known good
  let hi = commits.length - 1; // assumed bad (the current, broken state)
  let steps = 0;
  while (lo < hi) {
    const mid = Math.floor((lo + hi) / 2);
    steps++;
    if (isBad(commits[mid])) {
      hi = mid;
    } else {
      lo = mid + 1;
    }
  }
  return { firstBadCommit: commits[lo], steps };
}
```

This is genuinely how `git bisect` works underneath: repeatedly ask
"good or bad?" at the midpoint of the remaining range, and narrow
based on the answer, exactly like binary-searching a sorted array.

## Atomic history: 16 commits, bug introduced at commit 11

```js
const atomicCommits = Array.from({ length: 16 }, (_, i) => `c${i}`);
const bugIntroducedAt = 11;

function isBadAtomic(commitId) {
  return atomicCommits.indexOf(commitId) >= bugIntroducedAt;
}

console.log(bisect(atomicCommits, isBadAtomic));
// { firstBadCommit: "c11", steps: 4 }
```

Verified: bisect finds `c11` — the exact commit that introduced the
bug — in **4 steps**, matching `log2(16) = 4` exactly. Because each
commit is atomic, "the commit bisect points to" and "the change that
caused the bug" are the same thing. There's nothing left to search.

<Checkpoint question="In the atomic run above, bisect returned firstBadCommit: 'c11' after 4 steps. Is any further investigation needed to know exactly what caused the bug, or is the search over?">

The search is over. Because every commit in `atomicCommits` holds exactly
one logical change, `c11` isn't just "the commit where the bug first shows
up" — it's the actual change that caused it. There's no diff left to read
line by line and no ambiguity about which part of `c11` is responsible,
because `c11` doesn't contain any unrelated changes to sort through. That's
the specific payoff atomicity buys: bisect's output and the answer to "what
broke it" collapse into the same thing.

</Checkpoint>

## Bundled history: the same 16 logical changes, 8 of them merged into one commit

```js
const bundledCommits = [
  "c0",
  "c1",
  "c2",
  "c3",
  "c4",
  "c5",
  "c6",
  "c7",
  "megaCommit",
];
// megaCommit bundles what should have been 8 separate atomic commits (logical changes 8-15)
// the bug (originally at logical position 11) is somewhere inside it

function isBadBundled(commitId) {
  return bundledCommits.indexOf(commitId) >= 8; // megaCommit tests "bad"
}

console.log(bisect(bundledCommits, isBadBundled));
// { firstBadCommit: "megaCommit", steps: 3 }
```

Verified: bisect correctly finds `megaCommit` in **3 steps** — bisect
itself still works exactly as designed. But `megaCommit` bundles 8
unrelated logical changes, and bisect has no way to search _inside_
a single commit. Whichever of those 8 changes actually caused the bug
still has to be found by manually reading the diff — the predicted
outcome from the scenario above: fewer steps to find the commit,
but the commit's answer isn't actually actionable on its own.

<Checkpoint question="Bundled history found the culprit in 3 steps instead of the atomic history's 4 — fewer tests. Does that make the bundled history's bisect run more useful overall? Why or why not?">

No — fewer steps to find the commit is a shallower win than it looks,
because the step count only measures how fast bisect narrows the _search
space_, not how much work is left once it stops. The bundled run's 3 steps
land on `megaCommit`, which still contains 8 unrelated logical changes —
exactly the manual diff-reading bisect was supposed to replace has to
happen anyway, just starting one level later. The atomic run's 4 steps look
"slower" but end with nothing left to do. Step count and actionability are
different axes, and a bundled history trades a small amount on the first
for a large loss on the second.

</Checkpoint>

## Extend it: what if the history were 64 commits instead of 16?

**Using the same atomic-commit setup, how many steps would bisect need
across 64 commits instead of 16?** Predict from the pattern first —
`log2(64) = 6` — then verify:

```js
const commits64 = Array.from({ length: 64 }, (_, i) => `c${i}`);
const bugAt64 = 50;
console.log(bisect(commits64, (id) => commits64.indexOf(id) >= bugAt64));
// { firstBadCommit: "c50", steps: 6 }
```

Verified: **6 steps**, exactly `log2(64)`. Quadrupling the history size
from 16 to 64 only added 2 more tests, not 4x as many — this is the
concrete payoff of binary search that makes bisect practical even
across years of commit history, as long as the commits stay atomic
enough for its answer to mean something.

## Failure modes

| Failure mode                                                                | What it gets wrong                                                                                                         |
| --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Assuming bisect finding a commit means the investigation is done            | It's only done if that commit is atomic — a bundled commit still needs a manual search inside it                           |
| Batching a work session into one commit for convenience                     | Feels efficient in the moment, but destroys the specificity that makes bisect's answer, code review, and revert all useful |
| Writing a vague message because the commit already speaks for itself        | Someone reading `git log` later shouldn't have to open every diff just to know what kind of change each commit represents  |
| Treating conventional commit types as a formatting rule with no real effect | The types are what makes scanning history fast — skipping them just moves that cost onto every future reader               |
| Assuming atomic commits mean smaller commits, always                        | Atomic means "one logical change," which can still be large — the point is coherence, not commit size                      |
