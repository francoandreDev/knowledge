Two reviewers spot the exact same bug in the exact same pull request: a
lookup inside a loop that's going to be O(n²) once the input list
grows. Reviewer A comments **"This is wrong, use a hashmap."** The
author doesn't reply for three days, then pushes a defensive comment
explaining why they did it that way, and the PR drags on for another
round. Reviewer B, on a different PR with the identical bug, comments
**"Nice catch on the edge case above — one more thing: this lookup
runs inside the loop on line 42, so it'll go quadratic once `items`
grows past a few hundred. Worth swapping to a `Map` here?"** The
author replies in twenty minutes with a fix. **Same bug, same
technical correctness, same reviewer skill — so what actually cost
Reviewer A three days that Reviewer B didn't spend?**

## The two things a review comment always carries

Every review comment does two jobs at once, whether the reviewer means to or not: it identifies a **technical fact** ("this will go quadratic"), and it sends a **social signal** about how the reviewer is treating the author — as a colleague solving a problem together, or as someone who made a mistake. Reviewer A's comment got the technical fact exactly right and the social signal exactly wrong. The bug report was correct; the delivery told the author "you did this wrong," which is a claim about the author, not about the code.

That distinction — fact vs. signal — is the entire subject of this unit. Getting it wrong doesn't make the review incorrect; it makes it expensive.

## What "expensive" actually looks like

| Signal in the comment                               | What the author does next                                            | Cost                                                         |
| --------------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------ |
| Blunt, person-directed ("you did this wrong")       | Reads it as criticism, drafts a defense before fixing anything       | Delay while the author manages the feeling, not just the fix |
| Vague ("this seems off")                            | Doesn't know what to change, has to ask a clarifying question        | An extra round-trip before any fix starts                    |
| Specific and code-directed, framed as a question    | Reads it as a technical fact, evaluates and fixes it directly        | Fix lands in the same sitting                                |
| Batched with unrelated nitpicks, no severity marked | Can't tell what's blocking vs. optional, fixes everything to be safe | Time spent on low-value changes, real issue buried           |

The pattern across all four rows: the cost isn't the bug, it's whatever the author has to do that isn't fixing the bug — managing a feeling, asking what was meant, or guessing what actually matters. Framing that avoids that overhead isn't about being nice; it's about not adding non-technical work to a technical exchange.

## The two levers this unit covers

- **Person vs. code framing** — "you wrote a bug" targets the author as a person; "this will go quadratic" targets the code as an object. The technical content can be identical; only the grammatical subject changes, and that's what determines whether the author feels evaluated or informed.
- **Async review etiquette** — pull request review usually isn't a live conversation. A comment sits unanswered for hours, gets read out of context, and has no tone of voice to soften it. The etiquette layer (severity labels, response-time norms, batching related comments together) exists specifically to compensate for the information a live conversation would normally supply for free.

## What this unit covers

L2 builds the actual model behind Reviewer B's comment — three concrete levers (subject, specificity, and framing-as-question) that turn a correct-but-costly comment into one that gets acted on immediately, plus the async-etiquette layer that governs comments as a batch, not just one at a time. L3 works through real before/after PR comment rewrites on actual diffs, including where the technique fails (a genuinely blocking issue dressed up as a gentle suggestion) and how disagreement gets escalated out of an endless comment thread.
