Two teams work on the same 6 frequently-touched files — `auth.js`,
`router.js`, `db.js`, `utils.js`, `api.js`, `types.js` — over the same
10-day sprint. Team Gitflow opens one feature branch on day 1 and
doesn't merge it until day 10. Team Trunk merges to the shared trunk
every single day, so no branch ever lives more than 24 hours. On
merge day, Team Gitflow hits 4 files that were independently modified
on both trunk and their branch — a multi-hour conflict-resolution
session. Team Trunk, across the entire sprint, hit **zero** conflicts.
**Both teams wrote roughly the same amount of code, touching the same
files. What made one team's integration painless and the other's
genuinely difficult?**

## Before comparing strategies

- **Trunk** or **main** is the shared line of work the team treats as
  the current integrated version.
- A **branch** is a temporary label where someone can work without
  immediately changing trunk.
- A **merge** combines the branch's work back into trunk.
- A **feature flag** is a switch in the application that can keep new
  code inactive for users even after the code has merged.

This unit is about integration safety: how often the team brings
separate work back together. PRs, CI, and feature flags are related
tools, but the question here is narrower: how long does work remain
separate before the team checks whether it still fits with everyone
else's work?

## The shape of the problem

- Every branch that isn't merged yet is a bet that nobody else will
  touch the same files before it lands. The longer a branch stays
  open, the more time other people's work has to independently touch
  the same files — and the bet gets worse the longer it's held.
- A merge conflict isn't really about _how much_ code changed — it's
  about how much **independent, overlapping** change accumulated
  before anyone reconciled it. Frequent small merges reconcile
  overlap constantly, in small pieces; infrequent large merges let
  overlap build up and then resolve it all at once.
- **Trunk-based development** and **gitflow** aren't just style
  preferences — they're two different answers to "how long should
  work stay unreconciled with everyone else's work before it gets
  checked?" and that answer changes how much conflict resolution a
  team actually does, in total, over a sprint.

Strictly speaking, "both sides touched the same file" is not always a
literal Git conflict. Git can often combine edits in different parts
of the same file. In this unit, overlapping file touches mean
"integration attention is more likely needed"; the `merge` unit covers
the exact rules for when Git can and cannot combine lines
automatically.

## Key terms

- **Trunk-based development** — a workflow where branches are
  extremely short-lived (often under a day), merging back to a shared
  trunk frequently and continuously.
- **Gitflow** — a workflow built around longer-lived branches (feature
  branches, release branches) that stay separate from trunk for an
  extended period before merging.
- **Branch divergence** — how much a branch and trunk have each
  independently changed since they last matched — this grows the
  longer a branch stays unmerged.
- **Feature flag** — a runtime toggle that lets incomplete or
  in-progress code merge to trunk safely, without being active for
  users yet — one of the tools that makes frequent trunk merges
  practical even for work that isn't finished.

## What this unit covers

L2 works through why merge conflict cost scales with how long a
branch stays open, not with how much code it contains, plus what each
strategy actually trades off. L3 implements a real simulation of both
teams' 10-day sprint in code — the exact scenario above — and extends
it across a range of sprint lengths to see where the two strategies'
conflict counts actually diverge.
