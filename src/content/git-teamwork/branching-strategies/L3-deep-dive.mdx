**Before running the simulation: both teams draw from the same 6 hot
files, with trunk and the feature work each independently touching one
file per day. If trunk-based merges daily and gitflow merges once at
the end, which strategy do you expect to accumulate more _total_
conflicted files across the 10-day sprint — and why might the answer
depend on how long the sprint actually is?**

## Modeling both teams' work as daily file touches

This is not a simulator of Git's exact line-merge algorithm. It is a
small model of overlap risk and merge cadence: "how often do both
sides touch the same limited set of hot files before they reconcile?"
That is enough to study why long-lived branches can make conflicts
arrive in one large batch, even though real Git may auto-merge some
same-file edits cleanly.

```js
function mulberry32(seed) {
  return function () {
    seed |= 0;
    seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}

const hotFiles = [
  "auth.js",
  "router.js",
  "db.js",
  "utils.js",
  "api.js",
  "types.js",
];

function pickFile(rand) {
  return hotFiles[Math.floor(rand() * hotFiles.length)];
}
```

Each simulated day, trunk (other developers' merged work) and the
feature work each independently touch one randomly-chosen hot file —
this models realistic overlap risk without assuming either side
deliberately targets the same file.

## Trunk-based: merge every day, conflicts resolved immediately

```js
function simulateTrunkBased(rand, days) {
  let conflictedMerges = 0;
  for (let d = 0; d < days; d++) {
    const trunkFile = pickFile(rand);
    const branchFile = pickFile(rand);
    if (trunkFile === branchFile) conflictedMerges++;
  }
  return conflictedMerges;
}

const rand1 = mulberry32(42);
console.log(simulateTrunkBased(rand1, 10));
// 0
```

Verified: with seed 42, trunk-based hits **zero** conflicted merges
across the full 10-day sprint. Each day's merge only ever risks that
single day's overlap — a 1-in-6 chance per day — so most days simply
don't conflict at all.

## Gitflow: one branch, one merge, the whole sprint's overlap at once

```js
function simulateGitflow(rand, days) {
  const trunkTouches = new Set();
  const branchTouches = new Set();
  for (let d = 0; d < days; d++) {
    trunkTouches.add(pickFile(rand));
    branchTouches.add(pickFile(rand));
  }
  let conflictedFiles = 0;
  for (const f of branchTouches) {
    if (trunkTouches.has(f)) conflictedFiles++;
  }
  return conflictedFiles;
}

const rand2 = mulberry32(42);
console.log(simulateGitflow(rand2, 10));
// 4
```

Verified: with the identical seed and the identical 10-day file-touch
sequence, gitflow's single end-of-sprint merge hits **4** conflicted
files. Same underlying random draws as the trunk-based run — the only
difference is _when_ the overlap gets checked. Checking once, after 10
days of accumulation, surfaces conflicts that daily merges would have
caught and resolved individually, one file at a time.

## Extend it: does the gap keep widening at longer sprint lengths?

```js
for (const days of [5, 10, 20, 30]) {
  const r1 = mulberry32(42);
  const r2 = mulberry32(42);
  console.log(days, simulateTrunkBased(r1, days), simulateGitflow(r2, days));
}
// 5  -> trunk: 0, gitflow: 1
// 10 -> trunk: 0, gitflow: 4
// 20 -> trunk: 2, gitflow: 6
// 30 -> trunk: 5, gitflow: 6
```

Verified: gitflow's conflict count is bounded by the number of hot
files (6 total) — once the branch has touched most of them, there's
no more room for the overlap count to grow, since `conflictedFiles`
can never exceed `hotFiles.length`. Trunk-based has no such ceiling —
its count is a sum across independent daily checks, so it keeps
growing the longer the sprint runs. **At 30 days, the two strategies'
totals are nearly equal (5 vs. 6)** — the trunk-based advantage is
real and large at realistic sprint lengths (5–10 days), but it isn't a
law of nature; it's a consequence of resolving conflicts in small,
frequent pieces rather than one large one, and that advantage
specifically shows up when branches would otherwise stay open for a
meaningful fraction of the file set's total exposure.

## Failure modes

| Failure mode                                                                   | What it gets wrong                                                                                                                            |
| ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| Assuming trunk-based always means zero conflicts                               | It means small, frequent conflicts resolved immediately — not the absence of conflict, just a different distribution of it                    |
| Adopting trunk-based without feature flags for incomplete work                 | Code merged to trunk before it's finished needs a way to stay inactive for users — without flags, trunk-based just means shipping broken code |
| Assuming a longer branch is only risky because of _more code_                  | Two branches with identical code volume can have wildly different conflict risk depending on how long they stayed open, not how big they are  |
| Treating gitflow's isolation as strictly worse in every case                   | Work that genuinely shouldn't be visible on trunk yet (security-sensitive changes, major rewrites) benefits from real isolation               |
| Picking a strategy without considering the team's actual file-overlap patterns | A team where different people rarely touch the same files gets little benefit from either strategy's conflict-avoidance properties            |
