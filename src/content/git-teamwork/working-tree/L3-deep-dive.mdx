## The full transcript

```
$ git checkout feature-a
$ echo "shared config v1 - my local tweak" > shared-config.js
$ git status --short
 M shared-config.js
```

The edit exists only in the working tree — unstaged, uncommitted, and (per L1/L2) not
tied to `feature-a` in any way Git actually tracks.

```
$ git checkout feature-b
Switched to branch 'feature-b'
M	shared-config.js

$ git status --short
 M shared-config.js
$ cat shared-config.js
shared config v1 - my local tweak
```

The switch succeeds with no warning, because `shared-config.js` is identical between
`feature-a`'s and `feature-b`'s last commits — checkout has nothing to reconcile for that
file, so the working tree copy (including the uncommitted edit) is left completely alone.
**The edit is not lost yet** — it's sitting on `feature-b` now, functionally
indistinguishable from an edit someone made directly on `feature-b`.

```
$ git restore .
$ git status --short

```

This is the actual moment of loss. `git restore .` (the modern equivalent of
`git checkout -- .` from this track's `checkout` unit) discards every uncommitted change
in the current working tree, restoring every tracked file to its last-committed state.
The developer ran this to clean up something else entirely — but `shared-config.js`'s
edit was sitting in that same working tree, with no marker distinguishing "this belongs to
a different mental context" from anything else. `git status --short` now prints nothing:
the working tree is clean.

Git cannot recover this edit because it was never in a commit or stash. An editor's local
history, a backup tool, or an operating-system snapshot might have a copy, but that would
be outside Git. From Git's point of view, the safety net starts when work enters the
repository.

<Checkpoint question="Of the four numbered steps in this incident — edit, checkout feature-b, restore ., checkout feature-a — which one actually destroyed the edit, and why do the two checkouts get blamed anyway?">

Step 3, `git restore .` on `feature-b`, is the only command that discarded anything —
it wiped every uncommitted change in the working tree it ran against, including an edit
that had nothing to do with why the developer ran it. Both checkouts get blamed instead
because they're the commands that visibly "moved" the developer between branches, and
the loss only becomes visible after the second one — by the time `feature-a` shows the
old content, the actual destructive command is two steps back and easy to forget. The
lesson generalizes: when uncommitted work disappears around a branch switch, the switch
itself is rarely the culprit, because checkout only overwrites files it can prove differ
between two commits — a bare `restore`, `checkout -- .`, or `reset --hard` run on
_either_ branch is what actually throws work away.

</Checkpoint>

```
$ git checkout feature-a
$ git status --short

$ cat shared-config.js
shared config v1
```

Back on `feature-a`, `shared-config.js` shows its original committed content —
`"shared config v1"`, with no trace of `"- my local tweak"`. **The loss happened at step 3
(`git restore .` on feature-b), not at either checkout** — both branch switches were
completely uneventful. This is the core misdiagnosis in incidents like this: the natural
instinct is to blame the checkout, when the actual command responsible for the loss ran on
a different branch entirely, targeting a file the developer had already forgotten was
mid-edit.

## Why this doesn't happen with a genuinely diverged file

**Extend the incident: what if `shared-config.js` had already diverged between the two
branches before the edit — does the same silent loss still happen?** Re-run the same
sequence, but this time the target branch's committed version of the file is actually
different from the source branch's:

```
$ git checkout feature-a
$ echo "feature-a uncommitted divergent edit" > shared-config.js
$ git status --short
 M shared-config.js

$ git checkout feature-b
error: Your local changes to the following files would be overwritten by checkout:
	shared-config.js
Please commit your changes or stash them before you switch branches.
Aborting
```

Here Git refuses outright — because `feature-b`'s committed version of `shared-config.js`
genuinely differs, silently carrying the edit over risks either overwriting information or
producing a confusing merge, so Git stops before doing anything. The incident above was
only possible **because** the file happened to be identical between branches — the
"protected" case (genuine divergence) is actually the safer one; the "convenient" case
(no divergence) is the one that quietly set up the loss.

<Checkpoint question="Suppose the developer in this incident had, instead of running git restore ., run git stash right after the edit on feature-a, then switched to feature-b and back. Would step 3's git restore . on feature-b still have destroyed the edit?">

No. `git stash` moves the uncommitted edit into a dedicated stash entry, which lives in
the repository's stash list, not in the working tree — at that point the edit is no
longer "uncommitted work sitting on disk" that a bare `restore .` can see or touch.
`git restore .` on `feature-b` only discards uncommitted changes present in that working
tree at the time it runs; a stashed edit is untouched by it and can be reapplied later
with `git stash pop`, on whichever branch actually needs it. This is exactly why L1 and
L2's warning is to commit or stash _before_ switching, not to rely on the working tree's
silent carry-over behavior to keep an edit safe.

</Checkpoint>

## What actually would have prevented this

**Given that the edit was real, useful work, what single habit — not a different Git
command — would have prevented losing it?** Committing it (even as a disposable
`git commit -m "wip"`) or stashing it (`git stash`) before switching branches at all would
have moved the edit into the repository or a dedicated stash entry — both of which
`git restore .` on a _different_ branch cannot touch. The failure wasn't a Git bug or a
missing safety net; the working tree genuinely has no per-branch memory for uncommitted
content, and the fix is to stop relying on it having one.

Use this before changing branches when work is unfinished:

| What `git status` shows                 | Safer next action                                                          |
| --------------------------------------- | -------------------------------------------------------------------------- |
| It belongs to the current branch        | `git add` + `git commit`                                                   |
| It is useful but not ready to commit    | `git stash` before switching                                               |
| It is scratch you truly want to discard | `git restore <file>` with an exact file path                               |
| You are not sure                        | Do not run `git restore .`, `git checkout -- .`, or `git reset --hard` yet |

## Failure modes

| Failure mode                                                               | What it gets wrong                                                                                                                                       |
| -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Assuming uncommitted edits are tied to whichever branch you made them on   | The working tree has no branch affinity — an edit is just sitting on disk until it's committed, regardless of which branch is checked out                |
| Blaming the checkout for a loss that happened on a different branch        | The checkout itself only refuses or silently carries a file over — the actual data loss in this incident came from a cleanup command run afterward       |
| Assuming Git will always warn before discarding uncommitted work           | `checkout <branch>` warns when a file genuinely diverges; `restore .`/`checkout -- .`/`reset --hard` do NOT warn — they discard immediately and silently |
| Treating "no conflict on checkout" as proof nothing risky happened         | A clean, warning-free checkout can still leave uncommitted work sitting somewhere easy to lose track of and later discard by accident                    |
| Relying on memory instead of `git status` before running a discard command | A quick `git status --short` before any `restore`/`checkout --`/`reset --hard` would have surfaced the at-risk file before it was too late               |
