An engineer adds a "member discount" that stacks on top of any active
coupon. `applyDiscount(price, discountPercent)` hasn't changed, and
every existing test still passes — none of them happens to combine a
60% member discount with a 50% coupon. A reviewer, reading the diff
rather than running anything, asks one question: "what happens if the
combined discount goes over 100%?" Nobody had tested that combination
because nobody had written that combination before this PR made it
possible. **The tests were real and they all passed. What did the
tests structurally have no way of catching, and why did a human
reading the diff catch it instead?**

## The PR flow in plain words

1. The author creates a branch and makes a change there.
2. The author opens a PR, showing the diff and asking to merge it into
   `main`.
3. Automated checks run, and reviewers read the change.
4. The PR can merge only after the required checks and required human
   approvals pass.

| Word       | Meaning in this unit                                                     |
| ---------- | ------------------------------------------------------------------------ |
| `main`     | The shared branch the team treats as the integrated version              |
| Branch     | The author's temporary line of work                                      |
| Author     | The person proposing the change                                          |
| Reviewer   | A teammate who reads the change before it joins `main`                   |
| Merge      | Bringing the PR's branch into `main`                                     |
| Test suite | The automated checks that exercise expected behavior across the codebase |

## The shape of the problem

- Automated checks (tests, linters, type checkers) can only catch
  what someone already thought to encode as a check — they're
  powerful against regressions in things already tested, and blind
  to a genuinely new scenario nobody wrote a test for yet.
- A **pull request (PR)** isn't just "a way to get code into main" —
  it's a checkpoint where two different kinds of scrutiny (automated
  and human) get applied _before_ a change becomes everyone's
  problem, rather than after.
- **CI (continuous integration) gating** and **human review** aren't
  redundant with each other — they catch different categories of
  mistake, and a team that only has one of them has a real blind
  spot, not just a slower process.

## Key terms

- **Pull request (PR)** — a proposed change, presented for review and
  automated checks before it's merged into the shared branch.
- **CI (continuous integration) gating** — configuring the shared
  branch so a PR literally cannot merge until its automated checks
  (tests, linting, build) pass — turning "please run the tests" from
  a request into an enforced requirement.
- **Review culture** — the shared norms around what reviewers
  actually check for and how feedback is given — whether review
  means "skim and approve" or "actually engage with what changed and
  why."
- **Blocking check** — an automated check configured to prevent a
  merge on failure, as opposed to one that only reports a warning.
- **Diff review** — reading the actual lines that changed (and the
  reasoning behind them), as opposed to just re-running the existing
  test suite and trusting a green checkmark.

## What this unit covers

L2 works through what CI gating and human review each structurally
can and can't catch, and why a team needs both rather than treating
one as a stand-in for the other. L3 builds the discount-stacking bug
from the opening scenario in real code, shows exactly why the
existing test suite passed anyway, and walks through both directions
of the same lesson: a bug review catches that CI missed, and a
separate bug CI's full suite catches that a diff-only review would
have missed.
