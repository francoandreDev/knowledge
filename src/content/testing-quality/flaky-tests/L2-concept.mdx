## What can a correct test still secretly depend on?

**If the assertion is right, what else could change the result?** Anything
the test does not control:

| Hidden dependency | What it looks like                                  | Why the result varies                         | Deterministic fix                            |
| ----------------- | --------------------------------------------------- | --------------------------------------------- | -------------------------------------------- |
| Shared state      | Two tests use the same list or file                 | Result depends on which test ran first        | Fresh state per test                         |
| Real time         | Code reads the current clock or waits a fixed delay | Machines and moments differ                   | Pass in or freeze the time                   |
| Real randomness   | Random values with no fixed seed                    | A different value every run                   | Seed it, or inject the value                 |
| Unfinished async  | Assertion runs before the operation completes       | Depends on how fast the event loop gets to it | Wait for exactly the operation being checked |

Every row has a deterministic fix. Flakiness is not an unavoidable cost of
testing stateful or async code; it marks a dependency nobody pinned down.

<Checkpoint question="A test expects the string 'Monday discount' but the function reads the system date to choose the label. It passes on Mondays only. Which of the four is this, and what is the fix?">

It is the real-time dependency. The function's output depends on the actual
date, which the test does not control. The fix is to hand the function the
date as an input (or freeze the clock) so the expected value and the code
agree no matter when the test runs. Editing the expectation each week would
just move the failure to a different day.

</Checkpoint>

## How often does a small flake actually show up?

**A test fails on 5% of runs. Is that rare enough to ignore?** The chance of
at least one failure in `n` runs is `1 - 0.95^n`, assuming each run is
independent (an assumption: real flakes are sometimes correlated).

| Runs | Chance of at least one failure |
| ---- | ------------------------------ |
| 1    | 5.0%                           |
| 10   | 40.1%                          |
| 20   | 64.2%                          |
| 50   | 92.3%                          |

So a "rare" flake becomes a near certainty across a week of CI. The
interactive demo for this unit lets you drag both numbers.

## Which quick fixes treat the symptom?

**Rerunning the red build made it green. Is the problem solved?** No. The
dependency is still there:

| Quick fix                                     | What it does              | What remains                        |
| --------------------------------------------- | ------------------------- | ----------------------------------- |
| Re-run until green                            | Hides this failure        | The dependency, plus wasted CI time |
| Longer fixed delay before asserting           | Shrinks the timing window | A window still exists, now slower   |
| Reset the shared state at the top of one test | Fixes that one test       | Every other test must also remember |
| Fresh state built for each test               | Removes the shared object | Nothing: nothing is left to forget  |

<Checkpoint question="Why is 'fresh state per test' a stronger fix than 'each test resets the shared state first'?">

The reset approach depends on every author, forever, remembering a step; one
new test that forgets reintroduces the order-dependent bug. Fresh state per
test removes the shared object, so correctness no longer depends on anyone
remembering anything.

</Checkpoint>
