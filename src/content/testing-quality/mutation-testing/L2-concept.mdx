## What does a mutation tool do differently from running the tests once?

**It runs the whole suite many times, once per planted bug.** Each run is a
hypothesis: "if the code had exactly this mistake, would anyone notice?"

```mermaid
flowchart TD
    A[Original code + passing suite] --> B[Make one mutant:
    one operator at one place]
    B --> C[Run the full suite against the mutant]
    C --> D{Any test fails?}
    D -- Yes --> E[Killed: bug caught]
    D -- No --> F[Survived: gap found]
    E --> G{More mutants?}
    F --> G
    G -- Yes --> B
    G -- No --> H[Score = killed / total non-equivalent]
```

<Checkpoint question="A mutant survives. Does that mean the original code has a bug?">

No. The original code is never changed by the run; the mutant is a separate,
deliberately broken copy. A survivor means the suite would not have noticed that
exact bug if someone introduced it. It is a verdict on the tests, not on the
current code.

</Checkpoint>

## Which small bugs does a tool plant?

**Are the changes random?** No. A **mutation operator** is a rule that models one
common human mistake, so each operator asks a different narrow question.

| Operator               | Before        | After          | Question it asks the suite                  |
| ---------------------- | ------------- | -------------- | ------------------------------------------- |
| Conditional boundary   | `weight > 20` | `weight >= 20` | Does any test sit exactly on the threshold? |
| Arithmetic replacement | `a + b`       | `a - b`        | Does any test check the computed number?    |
| Statement removal      | `fee += 10`   | line deleted   | Does any test notice the line is missing?   |
| Return-value mutation  | `return fee`  | `return 0`     | Does any test check what comes back?        |

The operators are independent probes. A suite can kill every arithmetic mutant
and still let every boundary mutant survive.

<Checkpoint question="A suite kills 9 of 10 arithmetic mutants but 0 of 6 boundary mutants. Does the arithmetic result predict the boundary result?">

No. Each operator tests a different kind of mistake at different places. Strong
results on one say nothing about another, so diagnose gaps per operator or per
mutant, not from one blended percentage.

</Checkpoint>

## Why not run it on every commit?

**If one suite run takes 8 seconds, how long do 400 mutants take?** Each mutant
needs one full suite run, so total time is mutants times suite time.

| Mutants | One suite run | Total time    |
| ------- | ------------- | ------------- |
| 20      | 2 s           | 40 s          |
| 200     | 2 s           | about 6.7 min |
| 200     | 30 s          | 100 min       |
| 400     | 8 s           | about 53 min  |

So teams scope it: critical modules only (pricing, permission checks), run on a
nightly or weekly schedule, and treat the survivor list as a to-do list for
better tests rather than a merge gate. Use the slider on this unit's page to see
how quickly the total grows.
