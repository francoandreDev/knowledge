## How do you get from a stated request to the need underneath it?

**Mara says "add a CSV export". If you build it as written, you are betting
that export is the right fix. How do you test that bet before spending a
sprint?** You ask what the export is for, and keep asking.

The **five whys** asks "why do you need that?" after each answer and checks
whether the new answer names a **need** or just another tool. "Validate" here
does not mean a technical test; it means confirming with the person that you
understood the real difficulty.

```mermaid
flowchart TD
    A["Request:\nI want a CSV export"] -->|why?| B["So I can build\na report in a spreadsheet"]
    B -->|why?| C["So I can see how the number\nmoves week over week"]
    C -->|why?| D["So I know if it is getting worse\nbefore it becomes a crisis"]
    D --> E["Root need: early warning\nof a worsening trend"]
```

The first answer ("a report") is still a tool. Only the last one names a need,
and the export turns out to be one of several ways to meet it. A live trend
line on the dashboard might serve Mara better than a file she must open
weekly, but she never asked for that because the spreadsheet was the only
workaround she knew.

**Is more whys always better?** No. The statement gets more useful as you dig,
then less useful once it turns vague. This chart uses the unit's demo model
(illustrative values, not data):

```mermaid
xychart-beta
    title "Usefulness of the problem statement for choosing a build (demo model)"
    x-axis ["0", "1", "2", "3", "4", "5", "6", "7"]
    y-axis "Usefulness (%)" 0 --> 100
    bar [40, 55, 70, 85, 100, 75, 50, 25]
```

| Whys asked | What the statement sounds like     | What it lets you compare                     |
| ---------- | ---------------------------------- | -------------------------------------------- |
| 0          | "Build a CSV export"               | Only the export itself                       |
| 3          | "Notice a worsening trend in time" | A chart, an alert, or a weekly summary email |
| 6 to 7     | "Feel in control of my work"       | Everything, which in practice means nothing  |

Stop when an answer names a need that is specific enough to compare several
solutions against. Five is a rule of thumb, not a quota.

<Checkpoint question="A teammate keeps asking why until the answer is 'so I can feel in control.' Why is that a worse place to stop than 'notice a worsening trend in time to act'?">

"Feel in control" is true, but almost any feature could be defended with it, so
it cannot rank a chart against an alert against an export. The trend sentence is
specific enough to judge each option by whether it gets Mara the warning in time,
while still leaving room for several solutions. Digging stops paying off at the
point where the statement stops separating good options from bad ones.

## Why does the same need call for different solutions in different situations?

**Suppose Mara's need and an analyst's need both involve "seeing this number
over time." Would one CSV export serve both?** Not well. This is where jobs to
be done helps: people "hire" a product to make progress on a specific job in a
specific situation. "Job" means the progress someone wants, not their job title.

| Part                | Mara: the weekly glance                       | An analyst: the one-off deep dive             |
| ------------------- | --------------------------------------------- | --------------------------------------------- |
| The job             | Notice a worsening trend before it hurts      | Understand exactly why last month dropped     |
| The situation       | Routine, a few seconds of attention           | Rare, worth an hour of real analysis          |
| Best-fit solution   | A trend line already visible on the dashboard | Raw data to slice and filter freely           |
| Why the other fails | A raw file adds friction to a routine glance  | A pre-drawn chart cannot answer an open "why" |

```mermaid
flowchart LR
    N["Same underlying need:\nsee a number over time"] --> J1["Job 1: routine glance"]
    N --> J2["Job 2: open investigation"]
    J1 --> S1["Solution: live trend line"]
    J2 --> S2["Solution: raw export"]
```

A generic CSV export fits the second column reasonably and the first badly, and
the first column was Mara's. Naming the job, not just the data, is what picks
the solution.

<Checkpoint question="Both jobs touch the same raw numbers. Why does naming the job still change what you build?">

Because the two jobs put opposite demands on the solution. The weekly glance
needs the answer to be there with zero extra steps; a file adds friction. The deep
dive needs freedom to ask a question nobody anticipated; a pre-drawn chart
blocks that. Same data, different situation, so a solution tuned for one
works against the other.
